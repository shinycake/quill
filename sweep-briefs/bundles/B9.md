## subsystems-12: The tray and dock badge recount every chat four to six times per update batch
- Severity: P3
- Kind: cpu
- Platforms: macOS, Windows, Linux
- Where: `src/ui/notifications/mod.rs:472-475` pokes `wake::CHROME` for each poll with updates. `src/main.rs:432-449` has no throttle (the menu loop at `src/ui/os_menus/mod.rs:408-409` has a 1 s one) and runs `sync_tray` and `sync_icon_badge`, each calling `total_unread`. `src/notify_accounts.rs:109-122` computes `badge_count` once or twice, and each `list_badge` (`src/tray/mod.rs:148`) runs `forum_topics_extra` (`:128`) over all chats. `poll_background` adds the same per ingest for each background account.
- Trigger: a busy account with many chats; the work is on the UI thread.
- Effect and size: inferred 2 to 3 passes per `of`, doubled by the two callers. At 4000 chats and about 50 ns per chat, that is about 1 ms per wake, so about 1% of the UI thread at 10 wakes per second. Forums with many topics add `topic_badge` per topic. Small for most accounts.
- Why it is real: `sync_with` dedupes the OS push, not the count, and `CHROME` is poked per batch.
- Fix sketch: compute `total_unread` once per wake and pass the value to both syncs. Throttle the loop to about 4 per second as the menu loop does, keeping the first update prompt. Better, skip the pass unless an unread-affecting update applied (a session revision bumped by the unread and forum reducers).
- Proof plan: a counting test: a wake with an unchanged revision does no pass. A test that the badge still lands within one wake after a change, driven by the epoch and not by a timer.
- Scope: `src/main.rs`, `src/tray/mod.rs`, `src/icon_badge.rs`, `src/notify_accounts.rs`. Low risk. May overlap the idle-wakeups lane.

## ui-thread-4: On Windows each notification builds a whole renderer on the UI thread
- Severity: P2 measurable waste
- Kind: stall
- Platforms: Windows by default. `src/notify/custom.rs:126-129` gives Windows `by_default = false`, so Quill's own windows are used unless the user opts in to native. X11 with a daemon without full parity too. macOS and Wayland never use these windows unless forced.
- Where: `src/ui/notify_windows/mod.rs:438` `cx.open_window` for each toast. On Windows it goes to `third_party/gpui-pre-windows/src/window.rs:152` `DirectXRenderer::new` to `directx_renderer.rs:178-206`: `DirectXResources::new`, `DirectXRenderPipelines::new` (eight pipeline states plus the HDR and NV12 sets), `DirectComposition::new`, and `create_swap_chain_for_composition` at `:1403`.
- Trigger: a message arrives while a toast slot is free. `clamp_count` limits how many are open, so a burst is paced by slots, but each toast is one full open and one full teardown.
- Effect and size: not measured. Guess 30 to 100 ms per toast on the UI thread, from the object count: an HWND, a swap chain, a composition target and about ten sets of shaders and states. This lands on whatever the main window is doing, such as a playing clip or a scroll.
- Why it is real: `open_popup` has no pool, and renderer objects are per window, not per device. Nothing shares them.
- What tdesktop does: also opens its own widget per toast, but a software-painted Qt window has no pipeline setup, so its cost is not comparable.
- Fix sketch: measure first, since the size is a guess. If confirmed, either share pipeline objects per D3D device (`DirectXDevices`), which helps every window, or keep up to `clamp_count` hidden popups for a short time after the last toast and reuse them. Pooling needs a move and resize path on each platform and holds swap chains, so the short lifetime matters. Prefer sharing unless the numbers say otherwise. Per-window instance buffers in `PipelineState` need care.
- Proof plan: a debug log with the time around `open_popup` on a Windows machine with 20 toasts, before and after. If pooling is chosen, a `TestAppContext` test counts `open_window` calls across dismiss and re-show.
- Scope: `third_party/gpui-pre-windows/src/directx_renderer.rs` and `directx_devices.rs` (record in `QUILL-CHANGES.md`), or `src/ui/notify_windows/`. Medium risk, Windows only. May overlap the Linux and Windows lane.

## ui-thread-5: The photo editor renders, encodes and rotates full-size pictures on the UI thread
- Severity: P2 measurable waste
- Kind: stall
- Platforms: macOS, Windows, Linux.
- Where: `src/ui/photo_editor.rs:358-364` (`EditorPurpose::MessageEdit`) and `:373-375` (`Attachment`): `render` (`src/ui/photo_edit.rs:133`) and `write_edited_png` (`src/ui/edit_media_tools.rs:30`), both inline. `rotate` at `src/ui/photo_editor.rs:164` and `flip` at `:181` transform the full working image and rebuild `preview_of`. `src/ui/photo_editor_items.rs:298` `sticker_pixels` decodes a sticker at click, and `:225` rasterizes an emoji.
- Trigger: Done in the editor for an attachment or a message edit, each Rotate or Flip click, adding a sticker.
- Effect and size: measured with the same calls on a synthetic 4032x3024 photo-like image with sensor-style noise, third round of three. Done: `clone` 1.3 ms, crop `to_image` 2.4 ms, PNG save 89.9 ms (21.8 MB), about 94 ms before strokes and stickers. Rotate: 12.3 + 33.9 = 46 ms. Flip: 10.2 + 33.9 = 44 ms. At 1920x1080: Done 15 ms, Rotate 15 ms. A 48 MP photo fits within `MAX_TEXTURE_EDGE`, so scale by four: about 370 ms for Done and 180 ms per Rotate (inferred). Each large placed sticker adds a full-size resize in `overlay_item` (`photo_edit.rs:207`).
- Why it is real: the `Profile` path (`src/ui/photo_editor_profile.rs:321`) and the `Set` path (`src/ui/sticker_set_box/creator.rs:236`) already run off thread through `run_off_ui_then`. Only these two purposes were left. The decode into the editor is off thread (`photo_editor.rs:319`), so the slow part is only the way out.
- Fix sketch: follow `finish_profile_crop`. Take the editor apart, run `render` and `write_edited_png` in `run_off_ui_then`, and apply the tray or message-edit update in `done`, with the existing check that the item is still in the tray. For Rotate and Flip, record the transform, turn only the 1600 px preview on the UI thread, and apply it to the full image in the same off-thread job. `sticker_pixels` moves to `run_off_ui_then` as well. `rasterize_emoji` stays on main on macOS (AppKit).
- Proof plan: `TestAppContext` test: `save_photo_editor` returns with the background executor paused, no file exists yet, and after `run_until_parked` the tray item points at the PNG. A closed tray item removes the file, as today. Rotate test: the working image pointer is unchanged and the final render matches the old pixel output for rotate, flip, crop and a stroke.
- Scope: `src/ui/photo_editor.rs`, `src/ui/photo_editor_items.rs`, `src/ui/edit_media_tools.rs`, maybe `src/ui/photo_edit.rs`. Low to medium risk: normalized crop, stroke and item coordinates must keep their order against a deferred transform.
