## growth-4: Forum topic and comment thread views have no window cap at all
- Severity: P3 minor
- Kind: leak
- Platforms: macOS, Windows, Linux
- Where: topic pages insert with no trim at `src/state/session_apply_messages.rs:245-248`. Thread pages do the same at `src/state/session_thread.rs:161`. `trim_window_end` has no caller for either. They are only cut to a tail once closed (`history_prune.rs:205`).
- Trigger: reading back through a long topic or a huge comment thread.
- Effect and size: inferred at about 3.5 KB per row while the view stays open, with the O(n) row passes from growth-1. 30,000 rows is about 100 MB, returned on leaving the view.
- Why it is real: R6 (`history_trim.rs`) was written for the main history only. `TopicHistory` (`src/state/search_types.rs:449`) has no newer-side paging, so it cannot drop its newest end today.
- What tdesktop does: topics and replies use `HistoryView::ListWidget`, a sliding window around the viewport (`_idsLimit`, `history_view_list_widget.cpp:806`, `:2509`).
- Fix sketch: `thread.history` can reuse `trim_window_end` as it already has `has_newer`, newer pages and `reset_window`. `TopicHistory` needs the same newer-page path before it can drop its newest end.
- Proof plan: state tests mirroring `history_window_cap_live.rs` for an older page past the cap in a thread and in a topic, then paging back down.
- Scope: `session_thread.rs`, `session_apply_messages.rs`, `search_types.rs`, topic paging in `src/connect`. Medium risk for topics, since the view has only ever had one edge. Overlaps growth-1 for live appends.
