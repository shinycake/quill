## Failures

1. **src/ui/inline_playback.rs:404-442 with src/ui/recording_state.rs:146-157, 314-324 (g-382, r3 item 1 owner decision). A fixed 100 ms poll re-expressed as a "deadline" so the guard stops matching.**
   - **What is wrong:** `step_after(started, now)` is `started + k * RECORD_STEP`, the next tick of a fixed 100 ms grid. The step still wakes every 100 ms for the whole capture whatever happens (window hidden, behind another app), exactly the r3 shape; only the arithmetic moved into `RecordingUi::next_step`, a helper the guard cannot see into. r3 gave two ways out: an owner-approved allow line `poll:QuillApp::arm_record_tick`, or arming to the capture's real deadlines. Neither was taken, and the integrator approved only the notify allow line. The decisions rows (docs/decisions/account-scoped-ui-state.md:10251, 10317) say "so it is a deadline and not a fixed re-arm", which is false.
   - **Fix (owner decision, pick one):**
     - Ask the owner for `poll:QuillApp::arm_record_tick` (reason: the waveform level is sampled every 100 ms only while a capture runs, held by `Capture::tick`); then restore the plain `now + RECORD_STEP` re-arm and delete `step_after`/`next_step`/`started`, or keep them but stop calling it a deadline.
     - Or arm the step to the capture's real deadlines (next chat-action refresh, the round-video limit, the device check) and take the 100 ms bar sampling/redraw from the frame clock while a window draws.
   - Fix the two g-382 doc rows to say what it is.
   - **Test:** for the allow-line route the existing `a_recording_steps_on_its_own_timer_while_no_window_draws` suffices; for the deadline route, a recording with no window drawing wakes only at its chat-action refresh and limit. Note also `step_tests` reads `Instant::now()` in a test (wall-clock read); use a fixed origin from the test executor or drop the test with the helper.

2. **src/ui/notify_windows/mod.rs:901-905 (`notify_windows_tick`, `None if open`). The 300 ms poll also runs when nothing waits for input.**
   - **What is wrong:** with no deadline and no window `WaitingForInput`, the clock still re-arms every 300 ms while any popup, the hide-all window or a corner sample exists. That covers a popup held by the hover or by a reply being typed, and the Notifications page's corner samples. Each step reads nothing (`notify_check_input` only looks at waiting windows) and changes nothing; the r3 code stopped the clock here and the hold ends on an event that calls `ensure_notify_clock`. The r2 decisions row already recorded "The `open` poll is gone"; this brings it back. tdesktop's `_inputCheckTimer` runs only while a notification waits for input (`checkLastInput` restarts it only then). The approved exception is the idle read; a poll with nothing to read is not part of it.
   - **Fix:** delete `let open = ...` and the `None if open` arm, so `None` stops the clock as in r3. The `waiting` arms stay. Reword the `arm_notify_clock` doc (mod.rs:795) to "while a popup waits for the user".
   - **Test:** a shown popup held by the hover (`hovered = Some(id)`, hold not waiting) or a corner sample alone: after one step `windows.clock` is `Clock::Stopped`; a waiting popup in the same state keeps the clock running at `INPUT_CHECK_MS`.
