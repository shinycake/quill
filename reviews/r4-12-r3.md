## Failures

1. **src/ui/vanish/settle.rs:404-415 with src/ui/vanish.rs:547-555 and :701. Regression, S3, confirmed by reading.**
   - What is wrong: `settle_ghosts` changes `deletion` to `Local` only for ghosts that are already `Crumbling` when their answer is taken. In the usual order, the `ok` to `deleteMessages` is taken while the ghost is still `Waiting`, in the poll pass before the render that merges it. The ghost keeps `Deletion::Sent(request)`, and `merge_vanishing` carries that into `Crumbling { deletion: Sent }`. No answer for that request will come again.
   - Effect:
     1. At `DUST_LIFE` the phase is `Done`.
     2. `prune_vanishing` keeps the ghost because `live.is_some() && held_request(ghost).is_some()`.
     3. `vanish_overlay` counts it as running (`!ghost.is_waiting()`), so it requests 60 fps animation ticks.
     4. This goes on until some later poll pass runs `settle_ghosts`. On a quiet account that can take a long time, so a finished delete animation keeps the window repainting at 60 fps.
   - Fix:
     - In `settle_ghosts`, set `deletion = Deletion::Local` for every ghost, Waiting or Crumbling, whose request is in `answered` and was not refused. The answer is consumed, so nothing is left to forget.
     - In `vanish_overlay`, also count a ghost whose `phase(now) == Phase::Done` as not running.
   - Test: a `settle_ghosts_for_test` case where a `Waiting{Sent}` ghost's `Answer::Done` is taken. Assert that `held_request` is `None` afterwards, so `prune_vanishing` drops it at `Done` without a poll.
2. **src/ui/video_player/backend_ffmpeg.rs:285-290 and :389. S4, confirmed by reading. The previous item is not fixed.**
   - What is wrong: every player shares one wake slot. If the first player is still opening when a volume reopen drops it, its decode thread still runs `Decoder::start`, which calls `open_settled` (decode_loop.rs:86, :114). The opener's `Err` path does the same. Nothing checks `is_stopped` first. The old player's forwarder takes the shared wake and fires it while the new player is still opening. The new player's forwarder then finds the slot empty, so the real open is not redrawn. That is the bug the item described.
   - Fix: on reopen, move the wake into a fresh slot (`let wake = old_slot.lock().ok().and_then(|mut w| w.take()); self.open_wake = Arc::new(Mutex::new(wake));`) before registering `forward_open` on the new player, so the dropped player's forwarder points at an empty slot.
   - The test `a_reopen_for_volume_keeps_the_open_wake_and_fires_it_once` (:577) passes without the fix: the old code also fires once, early. Replace it with a test that uses a demuxer whose `info()` blocks on a channel, so the first player is mid-open at `set_volume`. Release it and assert that the wake has not fired (`try_recv` is `Err`). Then let the new player open, and assert that the wake fires.

7. **src/ui/updates.rs:62-74. Behaviour change, S4, plausible.**
   - What is wrong: from `DownloadFailed`, the timer only retries the kept release and never runs a check again. A release that fails for good stays stuck, for example on a checksum mismatch in a bad release or an asset taken down.    - Test: `DownloadFailed` with a checksum reason, then `recheck_for_updates`, then the state is `Checking`.
