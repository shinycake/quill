## Failures

1. **src/ui/mod.rs:79-80: hotspot edit that can be avoided (`#[cfg(test)] mod driver_fixture;`).**
   - What is wrong: `mod-lines` allows only the `mod` line, and the `#[cfg(test)]` attribute fails the check. The fixture is test-only support used by three test modules (auth_state.rs, bottom_action.rs, bar_report.rs), so it does not need to be declared in the shared module list.
   - Fix:
     - Remove the two lines from src/ui/mod.rs.
     - Declare the fixture inside a feature module, e.g. at the end of src/ui/auth_state.rs: `#[cfg(test)] #[path = "driver_fixture.rs"] pub(in crate::ui) mod driver_fixture;`.
     - Change the three imports to `crate::ui::auth_state::driver_fixture::{..}`.
   - Drop the `Hotspot-change:` trailer from d3cc698cc. Reword that commit, since the check reads every commit from the merge base.
   - Required: `bash scripts/check-hotspots.sh origin/claude/sweep-r4` passes with no trailer.

2. **src/ui/on_screen.rs:542-545: hotspot edit that can be avoided (`self.screen.auth_ui.submit.new_client()` in `put_on_screen`).**
   - What is wrong: `on_screen.rs` allows only a new `OnScreen` field. The reset belongs in the feature's own type.
   - Fix:
     - Make the stage carry what makes its id unique: `AuthSubmit::Out { request: RequestId, screen: ScreenEpoch }`, filled from `self.screen_epoch()` in `send_auth`.
     - `is_out(requests, epoch)` and `settle(requests, epoch)` treat an `Out` of another epoch as `Idle`. `screen_leaves_later` moves the epoch before a restarted client is put on screen (connect_ui.rs:304-305).
     - Before relying on this, verify that every `take_live` → `put_on_screen` path moves the epoch. If one does not, use the TDLib client id from `LiveSender` as the stamp instead.
     - Delete `AuthSubmit::new_client` and the on_screen.rs lines.
   - Test: replace `a_new_client_holds_no_old_request`, which only asserts that a setter sets. Build `Out { request: R, screen: E }`. With a registry that still holds R, `is_out(.., E.next())` is false and `is_out(.., E)` is true.
   - Drop the trailer (see item 1).

3. **src/ui/composer/send_bot_command.rs:100 with command_menu.rs:333: `MenuSendOutcome::Held` has no exit when the send goes out (r2 item 19). S3.**
   - What is wrong: `Held` keeps the reply, the typed token and the open menu, and nothing comes back to them. tdesktop re-runs `sendBotCommand` from `withPaymentApproved` (history_widget.cpp:6744-6765). That sends, then `cancelReply()` if `_replyTo == request.replyTo`.
   - Trigger: in a chat that charges Stars, reply to a message, type `/st`, pick `/start` and press Pay.
   - Effect: the command goes out, but the reply bar stays, `/st` stays in the field and the menu stays open. The next message the user sends replies to the same message again.
   - Fix:
     - Hold the wait in the chat's value: `ChatUi::menu_send: MenuSendStage { Idle, Held { request: RequestId, reply: Option<ReplyTarget> } }`.
     - Per-window upkeep: when `!paid_send_is_held(request)`, either the release sent it (the request is still in the session's registry, or answered) or the discard dropped it.
     - On release, do what the `Sent` arm does: clear the reply if it is still `reply`, clear the token, close the menu, set the Sending note.
     - On discard, keep everything.
     - A chat change drops the stage with `ChatUi`. An account switch drops it with the screen.
     - The guard should report released vs discarded explicitly, e.g. `PaidGuard::outcome(extra) -> Held | Released | Discarded | Unknown`, and not leave it to be inferred.
   - Tests: in a paid chat, (a) a menu command with a reply is `Held` and keeps the reply; after `release_paid_send` and one upkeep, the reply is `None` and the field is empty. (b) The same with `discard_paid_send`: the reply and the token stay.

5. **src/ui/composer_state.rs:159-171 with src/ui/composer/sent_text.rs:147-155: armed clears are now pruned by "request not in the registry", which is also true for a request that was answered but not yet noted. S3, plausible.**
   - What is wrong: `ingest` removes the request from the registry and queues `SendAnswered` in `session.messages.sent_answers`. Only `finish_successful_sends`, in the screen's poll pass, turns `Asked(request)` into `Made`. A background account's answers stay queued until the account is back on screen and its first poll runs.
   - Trigger: send in account A, then switch to account B before the answer. The answer lands in A's background session. Switch back to A. The first frame's `per_window_upkeep` → `settle_left_sends` → `forget_lost_clears` runs before the first poll pass.
   - Effect: `request_waits` is false, the armed clear "settles" and is removed, and the later ack finds no clear, so the draft is not cleared.
   - Fix: count a queued answer as waiting, e.g. `|request| session.requests.get(request).is_some() || session.messages.sent_answers.iter().any(|a| a.request == request)`. Alternatively, note the queued answers (`note_send_answer`) at the top of `settle_left_sends`, before pruning.
   - Test: an armed clear for R. Take R from the registry and push `SendAnswered { request: R, .. }`. Run `settle_left_sends`: the clear is still there. Then `finish_successful_sends` and the ack: the draft clears.

6. **src/ui/background_accounts/mod.rs:248 and deleting.rs:314-322: `deleting: HashMap<AccountKey, Rc<Task<()>>>` encodes "deferred" as a finished task left in the map. IS.**

   - What is wrong: on `Deferred` the entry stays by design (nothing may open the folder this run), but it holds a task that has already returned.    - Test: start a deletion whose wait is `CloseWait::Never`. The entry is `Deferred` and the account does not start; a second Remove is refused.
