# Review of r4-01 (Opus, 2026-11-12). Verdict: fix round

- src/ui/edit_media_tools.rs:191-211 and src/composer/edit_media_tools.rs:47-49 (02-002 / g-499, behaviour regression plus unkeyed dodge). `download_file(...).ok().flatten()` now treats `Ok(None)` as a failure. In `send_auto_download` (src/connect/media.rs:263-268), `Ok(None)` means the file is already requested or already being downloaded (`should_download` is false while `downloads.is_requested` or `requests.has_download` is true, or while TDLib runs it), and that is the common case for a photo whose history row or viewer is already loading it. Trigger: open a photo message whose full-size file is still auto-downloading, start editing it, and pick Edit Image. Before this bundle it waited and opened the editor. Now it shows "Could not download, please try again" straight away. Also, `EditImageFetch::Downloading { request }` is never read: upkeep matches `{ file_id, .. }` and decides through `downloads.gave_up(file_id)`, so the RequestId was added only so the unkeyed rule stops matching. Fix: drop `request` from the variant. The download tracker owns the transfer, so the doc should say that and name `gave_up`/landed as the two exits. Treat `Ok(_)` as waiting again. For the stalled-auto case (`is_stalled_auto` makes `Ok(None)` with nothing running, so `gave_up` would fire next frame), send it as a user download (the `DownloadOrigin::User` path), which is not stalled, so the edit always gets a fresh transfer. Add a test where the photo is already downloading when Edit Image is picked and assert the stage stays Downloading, then opens the editor when the file lands.
