## Failures

- src/connect/communities.rs:103-117 (`create_community_with_photo`). The round-2 guard refuses only a create *with* a photo while one is `Creating`. Trigger: create a community for chat A with a photo, then for chat B without one before A answers. B passes the check, and line 113 overwrites `Creating{A, Some(photo)}` with `Creating{B, None}`. A's answer then no longer matches, and community A never gets its photo (S4). The refusal is also silent: it returns `Ok(None)`, so pressing Create does nothing and shows no note. Fix: refuse any create while `create` is `Creating { photo: Some(_), .. }`, whether or not the new one has a photo. Or enter `Creating` only when the new photo is `Some`, and leave the slot alone otherwise. Then set a note ("another community is still being created") on the refusal instead of returning silently.

- src/connect/group_calls/live_story.rs:311-313. When the paid-reaction commit cannot be sent (a transport refusal), the note is set to `Refusal::NotEnough.message()`, which tells the user they do not have enough Stars. That names the wrong cause (S4). Trigger: the sender refuses during a live-story star commit. Fix: set `live.note = Some(err.stage_line())`, keeping the send error from the `send_json` result instead of discarding it with `.is_err()`.

- src/connect/groups/group_type.rs:192 with :270-283 (`after_upgrade`). An entry is removed only by `capture_edit_after_upgrade`, which runs for envelopes in ingest (core/mod.rs:499). An `UpgradeBasicGroup` request that is lost and settled through `settle_lost_request`, or that is still out at logout or close, leaves its entry in the Vec forever. The edits that wait on it never run, and nothing tells the user (S4, no way out for the owner-gone and lost exits). Fix: in the error path for the upgrade purpose (the path `settle_lost_request` also takes), remove the entry by request id and call `run_edit_after_upgrade(edit, false)` so the save ends with its failure note. Clear `after_upgrade` where the group-type state is reset on logout.

- src/connect/emoji_sets.rs:588-592 with src/emoji/mod.rs (`lists.search` / `found_sets`, `lists.installed` / `installed_sets`). The lists' stages are `Fetch<()>`, and the data sits in separate Vecs that are reset by hand next to them (`lists.search.cancel()` then `found_sets.clear()`). These are two fields kept in step (IS). The same split leaks into src/connect/media_library.rs:36 and src/connect/message_menu.rs:710, which use `installed_sets.is_empty()` as the "loaded" flag. An account with no custom emoji sets therefore re-asks on every panel or menu open. Fix: make them `Fetch<Vec<StickerSetInfo>>` (`lists.search`, `lists.installed`), drop `found_sets` and `installed_sets`, read through `items()`, and test `lists.installed.is_idle()` (or `!is_ready()`) in media_library.rs and message_menu.rs instead of `is_empty()`.

- src/connect/masks.rs:176-185 (`reorder_mask_set`). `.requests.pending.values().any(|p| matches!(p.purpose, ...))` is `has_purpose` written out by hand, so the guard's name rule does not see it. This is the same shape as the folder_links item from the first review. It also re-checks `GetInstalledMaskSets`, which the `masks.installed` Fetch already holds. Fix: `let busy = self.session.mask_change_pending() || self.session.stickers.masks.installed.is_loading();`.

- src/connect/media_library.rs:110-118 and src/connect/message_menu.rs:615-619. The stage holds the request id (`loading_request`, `PackTitle::Asking(id)`), but the busy test also asks the registry whether that request is still alive. Both purposes already settle through their error paths (messages/error.rs:109, stickers/error.rs:55), and `settle_lost_request` takes those paths too. So the registry lookup is a second copy of the in-flight fact, and a re-reader will record it as a stage that outlives its request (IS). Fix: test only the stage (`loading_request(..).is_some()`, `matches!(.., Some(PackTitle::Asking(_)))`), and make sure the error paths for `EmojiPackTitle` remove the `Asking` entry.

- src/connect/message_menu.rs:443-478 (`moderate_message`). Each step sends its own request. A refusal on step 2 or later returns `Err` after step 1 (report spam, or delete all from sender) already went out, so the delete box shows a failure while part of the moderation is running (S4). This is the shape fixed in contacts `delete_synced_contacts`. Fix: track whether any step was sent. On a later refusal, return `Ok(())` with the refusal as a note (as `fetch_message_audience` collects `refused`), and return `Err` only when the first step itself was refused.

- src/connect/contacts.rs:430-432. The comment says the note names the contacts it could not remove, but the note is only `err.stage_line()`. Fix the comment to "the note says the second half did not go out", or add the count to the note.

- src/connect/chat_list/folders.rs:188-189. The doc says "In-flight deduped; the response always overwrites the cache." That is stale: only the answer matching the `Fetch`'s request lands now. Fix: "Deduped on the spec's `Fetch`; only the answer to the request it holds lands, and `updateChatFolders` outdates it."

- src/connect/deep_links.rs:238-239. The doc says "Generation-guarded like `resolve_inline_bot`." There is no generation: the deep-link stage holds the RequestId. Fix: "The flow's stage holds the request; only its answer advances it."

- Untranslated literal UI strings in bundle files: auth.rs:130 and :149 ("not sent"), contacts.rs:23, :44 and :68, forum_saved.rs:91 and :314, groups/forum.rs:51 and :111, groups/mod.rs:171 ("could not send the request"), deep_links.rs:359, :405 and :490 ("Couldn't reach Telegram."), gift_manage.rs:628, marketplace.rs:57 and :141, masks.rs:43-47, and message_menu.rs:106. Where these reach a stage line the user sees, they are English-only and name no cause. Fix: pass `err.stage_line()` from the send error (already translated, and it names the cause), or a `keys::` entry run through `tr`.
