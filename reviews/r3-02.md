# Review of r3-02 (Opus, 2026-11-12). Verdict: merge after these fixes

Line numbers are on origin/claude/sweep-r3-02.

All 13 ids are addressed in code (none skipped). 05-001, 05-002, 05-003, 05-005, 05-006, 06-001, 06-002, 07-004 and 07-006 hold up: the stages carry their `RequestId`, answers are matched by request, and the dropped-request sweeps exit their stages. The new `rawid` guard and the baseline lines it adds are fine: they are existing hits outside this bundle, and no allow-list entries were added (two were correctly removed). The defects:

- **07-003 regression: the own-member probe is skipped for supergroups, so admins lose their rights.** `ChatSummary::rights_fetched` (src/state/chat_types.rs:447) is now true for any `OwnMember` other than `Unknown`/`Restricted(None)`. `updateSupergroup` runs `adopt_supergroup_status` (src/state/session_members.rs:127-158, the `None =>` arm). That arm calls `set_member_status(status, None)` (chat_types.rs:466), which sets `Other(Member)` or `Administrator(AdminRights { post_messages: None, .. })` before `getChatMember(me)` is ever sent. `maybe_probe_channel_membership` (src/connect/groups/mod.rs:178-183) then sees `rights_fetched()` and never asks. A supergroup administrator keeps an all-`None` `AdminRights`, so `can_invite_users` (chat_types.rs:493), `chat_can_restrict_members` and the other admin gates read false. Before this branch, `my_restriction` stayed `Unknown` until the probe, so the probe always went out. A second problem: when the probe fails while `updateSupergroup` said Restricted, `adopt_supergroup_status_for_chat` keeps `Restricted(None)`, and `note_no_member_record` (chat_types.rs:456) only settles `Unknown`. `rights_fetched` stays false and the probe is sent again on every pass, so the "a refused probe settles it" rule is broken. Fix: give a status known only from `updateSupergroup` or an optimistic change its own variant (e.g. `OwnMember::StatusOnly(ChannelMemberStatus)`, which `rights_fetched` treats as not fetched). Let only `record_own_member` produce `Other`/`Restricted(MemberRestriction)`/`Administrator(rights)`. Have `note_no_member_record` turn `Unknown` or `StatusOnly(s)` into a no-record value that keeps the status (e.g. `NoRecord(Option<ChannelMemberStatus>)`). Add tests: (a) a supergroup whose `updateSupergroup` says administrator still sends `getChatMember(me)`, and gets `can_invite_users` from its answer; (b) a refused probe for a Restricted-by-supergroup chat is not sent again.

- **06-002: `qr_settle_dropped_requests` reports progress on every poll while anything waits.** src/ui/peer_qr/mod.rs:735 returns `session_waits || free.is_some() || save.is_some()`. While a save, the gifts page, the contact link or a free code is in flight, `drain_peer_qr` (mod.rs:666 and :672) returns true on every pass, even with the box closed (`saves`/`gifts`/`contact_link` count). `poll_live` then forces `RedrawNeed::Now` and runs `progress_inline_mode` on every poll until the answer comes. Fix: return true only when something changed. `PeerQrData::forget_dropped` should return whether it dropped or failed anything, and the two `qr_act` calls count only when they fire (a request not found in `pending`).

- **07-002: `Writer::Running` has no exit when its thread dies.** `Saver::start_writer` (src/settings/window_save.rs:71-80) treats `Running` as live forever. If `run_writer` panics, the stage never returns to `Idle`, and every later `save_staged_window_state` only stages; nothing is written until the quit flush. The same happens if the `writer` lock is poisoned: `run_writer` then returns early without resetting. Fix: in `start_writer`, treat `Writer::Running { thread }` whose `thread.is_finished()` as `Idle` and start a new writer (as `launcher_worker_runs` does in icon_badge.rs), and rename `_thread` to `thread` since it is now read.

- **05-004: the test depends on the wall clock.** `a_worker_that_ends_hands_its_pending_count_back` (src/icon_badge.rs:623-637) drops a `WorkerEnd`, which stamps `Failed { at }` with the real `Instant::now()` (icon_badge.rs:451). It then retries at `t0() + 2 * FAILED_RETRY_AFTER`, where `t0()` is a process-wide `OnceLock` set by whichever icon_badge test ran first. If more than 10 s pass between that first call and this drop (a loaded CI runner, `--test-threads=1`), the retry is not due and the assert fails. Fix: in the test, read `let now = Instant::now();` after the drop and retry at `now + FAILED_RETRY_AFTER`. Or let `WorkerEnd` take its clock, so the test can pass `t0()`.

- **07-001: the test races on process globals.** `corrupt_registry_that_cannot_be_moved_aside_is_never_overwritten` (src/settings/accounts.rs:841-862) asserts `renames == 1` after a second load (accounts.rs:854). That holds only while the single-slot `LOADED` cache and the global `REGISTRY_WRITES` counter stay untouched between the two loads. Tests in this module run in parallel: `corrupt_registry_keeps_the_wipes_the_user_asked_for` saves and `accounts_added_from_two_threads_are_both_kept` calls `add_account`, both bumping `REGISTRY_WRITES`, and `missing_registry_falls_back_to_primary` replaces `LOADED`. Any of them invalidates the cache, the file is parsed and renamed again, and the test flakes. Fix: pass the cache slot and the write count into `load_registry_via`, so the test owns a local `Option<Loaded>` and a fixed count. Or drop the rename-count assertion and keep the deterministic ones (save refuses, file bytes intact).
