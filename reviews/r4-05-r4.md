## Failures

1. **A refusal that lands after its screen was left still comes back on the next open.** Locations: settings/error.rs:127, :157, :203, :216, :288 and stickers/masks.rs:305.
   - Every refusal arm calls `ChangeNote::refused` whether or not the screen is open.
   - The only exits are the screen's leave or close and the next change of the same kind. The note itself has no way to tell whether its owner is still there.
   - Trigger: offline (TDLib holds the request until it connects), block or unblock a user, then leave the Privacy page or close Settings.
     - The connection comes back and the refusal lands. `block_note` is set with no page open.
     - Opening Privacy hours later shows "Could not change the block list".
     - The same happens with a terminate or device link (Devices), a disconnect (websites box) and a mask change or reorder (manager closed before the answer).
   - This is the round-3 bug again, in a smaller window. The leave clears only what was already recorded.
   - Fix, either of these:
     - **(a)** Clear each note where its screen opens as well:
       - `arrive_settings_page(Page::Privacy)` → `leave_blocked_list()`
       - `arrive_settings_page(Page::Devices)` → `leave_sessions()`
       - `open_websites` → `leave_websites()`
       - `set_dialog_open(true)` → `change_note.clear()`; this one can simply clear on both edges.
     - **(b)** Make `ChangeNote` record only a refusal of a request it holds: `begin(request)` at the send, and the leave drops it. A refusal of a request the note no longer holds then lands nowhere. This matches "every answer is matched to what asked" better.
   - Test, one for each of the four notes, driven by the reducer and not by writing the note directly:
     - send the change
     - leave or close the screen
     - feed the real error envelope (`Session::apply` with the change's `RequestId`)
     - reopen through the same entry point the UI uses
     - assert `line().is_none()`
   - With (b), also assert that the refusal is shown when it arrives while the screen is open.

2. **docs/decisions/account-scoped-ui-state.md:10278 and the round-4 hotspot row state facts that are not true.**
   - "no commit carries a `Hotspot-change:` trailer" and "the `Hotspot-change:` trailer is gone" are both false: 5552e8907 keeps it in the bundle's history. Only the squashed bundle has no trailer.
   - The round-4 notes row says `a_refused_changes_line_ends_with_its_screen` "reopens each". It reopens only the mask manager, and that reopen asserts nothing a clear on close had not already ensured.
   - Fix: say the trailer stays on 5552e8907 and that the check passes on the squashed bundle (which integration produces). Describe what the test does, plus the new test from failure 1.
