# Review of r3-01 (Opus, 2026-11-12). Verdict: merge after these fixes

Line numbers are on origin/claude/sweep-r3-01.

- **03-002 not fixed for a delete (or create) that succeeds while the list loads.** `delete_folder_invite_link` edits the stale data under `Loading` (`src/connect/folder_links.rs:183-191`), and so does the create/edit upsert (`src/state/domains/chat_list/apply.rs:141-152`, `insert_data_if_missing` + `data_mut`). The stage still waits for the same `getChatFolderInviteLinks` request, so its late answer passes `answered` (`apply.rs:173`) and brings the deleted link back, or drops the new one. That is exactly the effect in the entry. Matching by RequestId does not help here: with the `has_purpose_for_folder` dedupe there is only ever one list request. The new test (`connect/tests/sweep_r3_01.rs:13`) only covers a *failed* delete. Fix: when a local link edit lands while `links.is_loading()`, call `links.outdate()` so the in-flight answer is dropped, and refetch once that request is gone (in the `ChatFolderInviteLinks` arm, when `answered` returns false and the list `is_outdated()`). Add a test for a successful delete followed by the late list answer.
- **01-001 only fixed for `promote_name`; a created or edited style still loses its front place.** `promote_front` puts a style the server has not listed yet into `self.styles` (`src/ai_compose/style.rs:85-91`, called from `src/state/domains/messages/ai_compose.rs:310` on a Create/Edit answer). `set_server` treats `before` (that same `self.styles`) as "the server held it" (`style.rs:70-79`). So an update that does not list the new style yet prunes it from `recent`, and it comes back in server order: the same bug through the other entry point. Fix: judge against the server's last list, not the local one. For example, make `recent` hold `Pending(name)` / `Listed(name)`: a name becomes `Listed` when a `set_server` list includes it, and only `Listed` names that are missing from a new list get pruned. Add a test: `promote_front(style("new", true))`, then a list without it, then a list with it; "new" must be first.
- **02-001: the edit's render job outlives the edit stage.** `RenderJob` is `Clone` (`src/composer/render_job.rs:52`). The edit bar's `Presence<ComposerEdit>` clones the whole `ComposerEdit`, including `media_edit.render`, on every frame (`src/ui/composer_ui/bar_slide.rs:58`, held in `Presence::last` and `Swap::from`, `src/ui/surface_reveal.rs:85-90`). After a cancel, the job and its task stay alive until the bar's exit slide ends and a later frame clears `last`, so "a cancelled edit drops the job, which cancels the render" does not hold. The doc comment "Only the stage clones it" (`render_job.rs:49-51`) is also wrong. Fix: have the edit bar follow a projection of `ComposerEdit` without `media_edit.render` (the fields `composer_edit_banner` draws), so the only long-lived holder of the job is the stage. Add a test that cancelling an edit with the bar drawn drops the job.
- **03-003 is only partly fixed: the group picker's installed sticker list still takes any answer.** `accept_installed_sticker_sets` still calls `lists.installed.succeed(())` (`src/state/session_stickers.rs:97`, reached by purpose only from `src/state/domains/stickers/apply.rs:48-51`). An older `getInstalledStickerSets` answer still lands over a newer load, which is the entry's effect. The decision doc skips it because "it has six senders outside this bundle". The brief does not accept that reason: make the smallest change outside the bundle and say so. Fix: pass the pending id and use `answered`, give every sender a `begin()` + `sent(extra)` (`src/connect/media_library.rs:37`, `src/connect/message_menu.rs:695`, `src/connect/sticker_creator.rs:235`, `src/connect/stickers.rs:163` and `:416`, and the demo seed `src/ui/composer_ui/mod.rs:40-41`), match the error by request in `stickers/error.rs:145`, and drop `unmatched:Session::accept_installed_sticker_sets 1` from `scripts/request-match-baseline.txt`.
- **The same "begun without its request" shape is left in a bundle file and baselined.** `src/connect/paid_reaction.rs:144-145` calls `paid.senders_asked(chat_id)`, which runs `Fetch::begin()` with no `sent` (`src/paid_reaction.rs:208-210`). The answer lands by chat via `succeed` (`src/paid_reaction.rs:198`, from `src/state/domains/settings/apply.rs:85-87`), and the error by chat via `fail` (`src/state/session_apply_error.rs:33-37`). `GetPaidReactionSenders` is not sweepable, so a lost request leaves the senders `Loading` for good: `can_ask_senders` stays false and the list is never asked again. The new `unsent` guard caught it, and the fixer added `unsent:PaidReactions::senders_asked 1` to the baseline instead of fixing it, which the file-complete rule does not allow for a touched file. Fix: `senders_asked(chat_id, extra)` does `begin()` + `sent(extra)`, `set_senders` and `senders_failed` take the pending id and use `answered` / `failed`, and the baseline line goes.
