## Defects introduced by the bundle

- **src/ui/folder_share/closed.rs:56-83, with invite.rs:21-55 (16-004 round 2): a queued link from a closed add overwrites a newer box. S3, confirmed.**
  - Trigger:
    1. Open addlist link 1 and press Add.
    2. Click link 2. It is queued in `Adding.next`.
    3. Close the box. `close_folder_invite` moves link 2 into `ClosedAsk::FolderAdded { next }`.
    4. Click link 3. `folders.invite` is None, so a new box opens for it. The user ticks chats.
    5. The add answers. `settle_closed_folder_asks` calls `open_folder_invite(link2)`.
  - Effect:
    - If link 3's box is Checking, Ready or Failed, `drop_folder_invite_check` and invite.rs:50 replace it with link 2. The user's newest click and their ticks are lost, and an older link pops up.
    - If link 3's box is Adding, link 2 overwrites its `next`, so a link 4 queued there is dropped.
  - Fix: a link queued behind a closed add gives way to anything newer. In `settle_closed_folder_asks`, open `queued` only when `self.folders.invite.is_none()`, and drop it otherwise. Or clear `next` on every `ClosedAsk::FolderAdded` when `open_folder_invite` opens a new box.
  - Add a test: close during the add, open link 3, answer the add, and assert the open box is still link 3.

- **src/ui/folder_share/closed.rs:42-47 and :56-73: queued links dropped without a word. S4, plausible.**
  - Trigger, either of:
    - Two closed adds that each hold a queued link answer in the same poll. `queued = queued.or(next)` keeps only the first.
    - A closed add whose answer the ring evicted is removed together with its `next`.
  - Effect: a link the user clicked never opens.
  - Fix: once the fix above is in, keep the newest queued link, not the first: replace `queued.or(next)` with `next.or(queued)` over the asks in request order. On eviction, open the `next` (subject to the same `invite.is_none()` rule) before removing the entry.

- **src/ui/gifs_ui.rs:374-382 with :516-517 (16-008 round 2): blank GIF tab once the bounded re-ask is spent. S4, confirmed.**
  - The loop from the last review is now bounded by `AskRound` (traced: at most two asks each way, and render sends nothing). Its end state is not drawn, though.
  - Trigger:
    1. In chat window B, search "x" and have it fail.
    2. Press in window A, which shows a kept "q".
    3. B asks "x" again (`Again`), and it fails.
    4. A takes the list back.
  - Effect: B is `Missing` + `Asked { round: Again }`. `gif_panel_status` returns no text for `Missing`, and `gifs_loading` needs `Live`, so the tab is blank, with no error and no spinner, until the user presses in B.
  - Fix: in `gif_panel_status`, when the section is `Missing` and the tab is `Asked { round: Again }`, show `Q_MISC_COULD_NOT_UPDATE_GIFS_TRY` (or a "tap to load" line).

- **src/ui/gift_market_state.rs:170-178, with gift_market_ui.rs:203-213, :253-281 and gift_auction_ui.rs:664: `from_send_box` derived from the recipient. S3, plausible.**
  - What is wrong: `begin_opening` sets `from_send_box: recipient.is_some()`. But the recipient is also set by a raised bid (gift_auction_ui.rs:664), and `open_gift_auction` resets it only when the market stack is empty.
  - Trigger:
    1. Under Active Auctions, raise a bid for another owner. The bid box stays open.
    2. Click a t.me/auction link (deep_link_routes.rs:107).
  - Effect: `from_send_box` is true while no send box is open, so the upkeep calls `end_opening()`. The auction never opens, and no note says why. Had the check passed, the bid would carry the previous auction's recipient.
  - Fix: pass the source explicitly, as `begin_opening(request, OpeningFrom::{SendBox, Elsewhere})`. Set the recipient from the send box, or to None, on every open.

- **src/ui/export_quit.rs:139-141: the hold's end closes whatever dialog is on top. S3, plausible.**

  - Trigger: while the alert is up, a shell box opens on the main window (shell.rs:526). Then the export finishes.
  - Effect: the other box closes and the alert stays.
  - Plausible only, because I did not confirm in the kit source that `open_dialog` stacks over an open alert.
  - Fix: keep the alert's handle or id in `Held { exit, alert }` and close only that dialog. Or have the alert dismiss itself when the gate is no longer `Held`.
