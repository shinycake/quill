# Review of r4-02 (Opus, 2026-11-12). Verdict: fix round

Every bundle id is either fixed or skipped with a test. The guards pass, and no allow or baseline line was added. The bundle still leaves guard housekeeping undone, and a fresh reader of the named files would still record the findings below.

## Failures

- scripts/request-match-allow.txt:3 and :5. `check-request-match.py --strict` reports two problems. `unmatched:Session::apply_earn` is gone: earn now answers by id. `purpose:ConnectDriver::drop_in_flight` is gone: the call moved into `RequestRegistry::supersede`. The default run also says "2 baseline line(s) can go". Fix: delete both allow lines and run `python3 scripts/check-request-match.py --prune`, then commit the pruned baseline.

- src/state/requests.rs (`supersede`) with src/connect/core/stale_fetches.rs (`drop_in_flight`). The body of `take_purpose` for every request of a purpose was moved into the guard-exempt requests.rs under a new name. The behaviour is the same one the old allow line justified (session-wide list, everything older than the mutation goes), so the move only hides it from the guard. Fix: keep the change, but add a doc comment on `supersede` that carries the allow line's reason ("every request of a session-wide list purpose is older than the mutation, so all go, not one by id"). Then a re-reader of requests.rs sees why a purpose sweep is right there and does not record it as a dodge.

- src/connect/folder_links.rs:35-43 (`fetch_recommended_chat_folders`). `.pending.values().any(|p| p.purpose == GetRecommendedChatFolders)` is `has_purpose` written out by hand, so the guard's name regex does not see it. Trigger: open the folder settings twice while the first ask is out. The second ask is refused because any request of that purpose exists, not because this list waits on it. Fix: give the recommended list a `Fetch` (or use the one it already has) and test `is_loading()`, or at minimum route it through `self.asked.is_out(...)` with `asked.sent` after the send, like the other stage-less asks in this bundle.

- src/connect/folder_links.rs:114-118. The `GetChatsForFolderInviteLink` half refuses on `has_purpose_for_folder` while `share.chats` is a `Fetch` that already holds that request. This is the same shape as 03-001, which this bundle fixed in folders.rs. Fix: test `share.chats.is_loading()` and drop the purpose check.

- src/connect/chat_list/folders.rs:239-245 (`fetch_chat_folder_chats_to_leave`). This has the same shape: `has_purpose_for_folder(GetChatFolderChatsToLeave)` sits beside the `folder_chats_to_leave` entry, a `Fetch` that holds the request. Fix: return `Ok(None)` when `folder_chats_to_leave.get(&folder_id).is_some_and(Fetch::is_loading)`, then call `begin()` and `sent(extra)` after the send.

- src/connect/chat_list/folders.rs:200-206 (`fetch_chat_folder`) with `folder_specs`. The spec has no Loading stage holding the RequestId. The busy check is per-folder purpose, and the answer is stored by folder id. Trigger: a `getChatFolder` goes out, the user edits the folder, and the old answer lands after the edit. It is stored as a fresh spec, and `finish_folder_removal` builds the removal edit from the pre-edit spec (S3). A failed send is also asked again on every ingest. Fix: give each `folder_specs` entry a `Fetch<ChatFolderSpec>`: `begin()`/`sent(id)` here, `answered(id)` in the reducer, and `outdate()` on `updateChatFolders`. The busy test becomes `is_loading()`.

- src/connect/chat_list/folders.rs:446-447 (`finish_folder_removal`). The busy test is "any `EditChatFolder`/`RemoveChatFromFolder` for this folder in the registry". That is an implicit stage for the removal (IS). Fix: hold the removal's request in a per-folder removal stage (`Removing { request }`), and refuse while it is set.

- src/connect/communities.rs:102 with src/connect/groups/community.rs:37. `CommunityCreate::Creating { request, photo }` is a single slot, but `create_community` refuses only per chat. Trigger: create a community with a photo for chat A, then for chat B before A answers. B overwrites `Creating{A, photo}`, A's answer no longer matches, and community A never gets its photo (S4). Fix: refuse a second create while `create` is `Creating` (check the stage, not the per-chat purpose), or key the photos by request in a map.

- src/connect/closing.rs:92-120 (`send_close`/`release_close`). The refused-close retry reuses `ShutdownPhase::HoldingClose { until }`, with an `until` that means nothing on that path: `release_close` resends at once because no hang-up is pending. Outside quit there is no cap, so a sender that keeps refusing gets `close` again on every drain (S4). Fix: add a distinct `ShutdownPhase::CloseRefused { retry_at }` with backoff, and let `release_close` resend only at `retry_at`.

- src/state/updates_sync.rs:388-392. The bundle moved the disk-pause state into the `DiskPauses` owner (03-007), but this function still mutates `settings.data_storage.disk_paused` directly and then calls `saved_changed()` by hand, so two fields are kept in step (IS). Fix: add `DiskPauses::forget_unheld(&mut saved, asked, held)`, which does the retain and marks the save itself, and call that here.

- src/connect/group_calls/mod.rs:84 with engine_sync.rs:70. `pump_group_call_transport` runs after every reducer update and passes `Wake::Update`, and a `Refused` setting retries on any `Wake::Update`. In a live call, participant/speaking updates arrive several times a second, so a refused mute or camera is still driven at update rate. For an active call the 03-005 effect only moves from the tick to the update stream (S4). Fix: retry on `Wake::Update` only when the update changed that call's own state (the `refused != wanted` arm already covers a user action), or treat `Update` like `Poll(Instant::now())` so the backoff holds. `Wake::at()` calling `Instant::now()` should also take the caller's clock.

- Asked ledger beside real stages: src/connect/emoji_sets.rs (`SetEmojiStatus` beside `StatusChange::Clearing/Setting`, `ChangeEmojiSet` beside `SetMutation::Running`, list purposes beside the list `Fetch`), src/connect/forum_saved.rs:270-297 (`load_saved_tags` topic 0 checks `asked.is_out` and then the `tags` Fetch that holds the same request), src/connect/forum_saved.rs:65-72 (`forum_topic_icons` with no stage, so an empty answer re-asks forever), src/connect/chat_appearance.rs:52-62 (default status ids beside an unstaged Vec). Where a stage already holds the RequestId, the ledger keeps a second copy of the same in-flight fact (two fields in step). Where no stage exists, `asked.is_out` is a purpose-keyed busy flag under a new name (rename). Fix: in emoji_sets.rs and the topic-0 tags path, drop the `asked.sent`/`is_out` calls and use the stage's `is_busy()`/`is_loading()`. For forum topic icons and default status ids, add a `Fetch` (Idle/Loading/Ready/Failed) and test `is_loading()`. Keep `Asked` only for mutations that have no screen stage (pin, read, clear, import, gif save, mask, group-type limit).

- src/connect/business_extra.rs (`lookup_business_bot`). A partial send failure resets the lookup to its default with no error, so the user sees the field go blank (S4). Fix: on a send error, call `lookup.failed(Some(extra))` with the send's stage line, so the field shows an error with Retry.

- src/connect/contacts.rs (`delete_synced_contacts`). It returns `Err` after the first request already went out, so the UI shows a failure while half the delete is running (S4). Fix: record the sent request in the delete stage before the second send, and return `Ok(Some(first))` with the second send's error stored as a stage note.

- src/connect/earn.rs (`request_earn_recipients`). It maps a real send error to `InvalidRequest`, so the stage line names the wrong cause (S4 nit). Fix: return the sender's error.
