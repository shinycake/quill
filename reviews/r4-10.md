## Failures

- **21-001 is not fixed. The new branch can never run.** `src/ui/send_box_media_check.rs:103-112` removes the JPEG only when `media.finish()` returns false inside `finish_media_check`. But the give-up task and the answer task are both held in `Read::Reading { _tasks }` (`send_box_state.rs:20-23`). When the 15 s give-up fires, `finish()` sets the stage to `Done` (`send_box_state.rs:69`), and that drops the answer task before it can call `finish_media_check`. `start()` replacing a read and `forget()` drop it the same way. The worker (`check_photo`) is synchronous: once it has started it still writes the JPEG into `quill-send-photos`, and its output is then dropped unread. The trigger in the register entry (a decode longer than 15 s) still leaves the file. There is also no test. Fix: make the file belong to the value. Return `MediaCheck::Jpeg(quill::scratch::TempFile)` from `check_photo` (as `finish_profile_crop` does with `TempFile` and `claim()`), and claim it in `apply_media_check`. An output dropped with a cancelled task, a give-up or a forgotten read then removes its own file. Delete the unreachable branch at 103-112. Add a test where `finish` loses to the give-up and the JPEG is gone afterwards. With the tasks in the stage, the `media_check_jobs` counter (`send_box_state.rs:116`) no longer guards anything a dropped task could deliver. Say so, or drop it.

- **21-004 is only partly fixed. Text still moves between the two-step views.** Back on the four `twofa_form_buttons` forms now clears the inputs (`src/ui/security/twofa_status_body.rs:384`). Every other way between views does not:
  - Recover's Back (`security_recovery.rs:417`)
  - LoginEmail's Back (`security_recovery.rs:635`)
  - the "Forgot password?" link (`security_recovery.rs:~427`, `twofa_forgot_link`)
  - `twofa_step_done`

  Trigger: Forgot password? → type a new password in Recover → Back → Change password. The New password field already holds the Recover text as dots. Type the current password, press Change, and the password becomes the one typed on another screen. Another trigger: an address typed in Login email, then Back → Recovery email, and that form opens with the login address in it. The register's fix was inputs owned per form, so a form only ever shows what was typed into it.

  Fix: clear in the one seam every view change goes through. Make `goto_twofa_view` (`twofa_state.rs:206`) and `twofa_step_done` take `window, cx` and empty the form inputs (current, new, hint, email, code) whenever the view changes, then drop the Back-only clear at `twofa_status_body.rs:384`. Also make `close_twofa` (`security/mod.rs:552-574`) call the same `clear_twofa_inputs` instead of its own copy. As it stands, `clear_twofa_inputs` (`mod.rs:665`) skips `code`, and `close_twofa` clears `status_check_password`, which is two lists kept in step by hand.

- **Wildcard maps three views to Turn off.** `src/ui/security/twofa_status_body.rs:374` has `_ => this.submit_twofa_password(window, cx, PasswordForm::Disable)`, which sends Status, Recover and LoginEmail to the destructive form. It cannot be reached today only because `submit_id` returns early (lines 345-352). Fix: give `twofa_form_buttons` a form type with exactly Enable/Change/Disable/Email (for example `enum TwofaForm { Password(PasswordForm), Email }`), so the match is total with no wildcard, or at least write `TwofaView::Disable =>` and make the other arms do nothing.

- **The 20-006 shape is still in the same file.** `src/ui/photo_editor_profile.rs:271-283` (`open_profile_photo_crop_file`, the camera shot's decode) and `:328` (`finish_profile_crop`'s render landing) still match their answer by `photo_target() == Some(target)`. Trigger: take a photo with the camera in a group's Edit box, then close and reopen that chat's Edit box before the decode or the "Set Photo" render ends. The shot or photo lands in the new box. Fix: hold the decode task in the sources stage (`hold_photo_pick`) and gate the landing with `end_photo_pick()`, as the picker and clipboard paths now do. Do the same for the crop render, or hold its task with the editor stage.

- **Rename: `Know::Asked(RequestId)` is never matched.** In `src/state/domains/messages/menu_actions.rs:14`, the answer and the error still land by purpose `(chat_id, message_id)`: `apply.rs:685` calls `set(chat, message, actions)` and `error.rs:160` calls `fail(chat, message)`. The `RequestId` in the stage is never compared, so an older ask's answer or error replaces a newer one's (menu `fetch_message_menu_actions` plus a hover refresh for the same row). Fix: pass `pending.id` to `set`/`fail` and apply only when the entry is `Asked(that id)`, or when it is not `Asked` (the menu's ask, which forgets first and records no `Asked`). Better still, have the menu path record `Asked(request)` too, so every answer is matched.

- **Regression in the gallery tick (21-002 change).** `src/ui/shared_media_select.rs:129-131`: ticking a row whose earlier ask failed used to ask again. Now `ask_shared_media_actions` returns at `known.is_failed(..)` (line 81), so the ticked `SelectedMedia` keeps unknown actions, and Forward/Delete for the selection stay restricted until the user right-clicks that row. Fix: on the tick path, forget the failure and ask (`fetch_message_menu_actions`, as the menu does). Keep the "no re-ask after failure" rule for hover only, and add a test for both.

- **20-003 / 20-004: the same-slot overwrite and the topic restore are left.** `src/ui/recording_send.rs:262` and `:372` register the clear when the file is ready, through `set_draft_clear`, and that replaces the slot's entry (`composer_sends.rs:469-477`). Trigger: tap Send on a voice note in chat A, then type and send a text in A before the encode ends. The voice's clear replaces the text's armed clear, the text's ack finds none, and if the voice send then fails the text draft is never cleared and comes back. This is the "overwriting that slot's own clear" in the entry's title, in its own slot. Fix: register the recording's clear when Send is tapped (the composer is consumed then) and attach the request to it when the send goes out, or let a slot hold one clear per send.

  Separately, `SendTarget::is_open` (line 74) compares the chat id only. A failed send restores the caption and reply into another topic of the same forum when the user switched topics. Fix: compare `Some(&target.slot) == self.send_slot().as_ref()` now that the target carries its slot.

- **Final re-read would record (IS): one recording lifecycle in two fields.** In `src/ui/recording_state.rs:119-121`, `RecordingUi::start: CaptureStart` and `RecordingUi::capture: Option<Capture>` are two fields for one lifecycle. `busy()` (line 258) is `capture.is_some() || starting()`, and `hold_started_video` (`recording_send.rs:449`) checks `wanted && !self.recording_active()` to keep the two from overlapping. Fix: one `enum Recording { Idle, Asking{..}, Opening{..}, Recording(Capture) }` that `begin_*`, `finish_start` and `hold_capture` move between. (The 20-005 skip of the three toggles inside `Capture` is fine. This is the field beside it.)

- **21-007 has no test, and the path fallback can act on the wrong copy.** In `src/ui/send_card/tiles.rs:470-482`, `tray_index_of` falls back to the first tray file with the same path. With the same file attached twice and the index shifted, Remove or Spoiler acts on the other copy. Fix: when the index no longer matches, give up rather than search by path. Or key `TrayItem` by something unique per attachment. Add the two-window test the entry describes: remove in one window, click in the other.
