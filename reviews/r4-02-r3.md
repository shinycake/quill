## Failures

- src/connect/emoji_sets.rs:648-658 (`refresh_emoji_pack_catalog`), together with src/connect/media_library.rs:36 and src/connect/message_menu.rs:724. This is a regression from the Fetch conversion. `installed_wanted` is `was_asking || !items().is_empty() || open`, so an installed list answered as empty (`Ready(vec![])`) is not asked for again when `updateInstalledStickerSets` comes. Before this round the media panel and the message menu re-asked whenever the list was empty, and that covered this case. Now they ask only on `can_ask() || is_outdated()`, and `Ready` is neither. Trigger: an account with no custom emoji sets has opened the media panel once and the Emoji Sets box is closed. A set is then added on the phone. TDLib sends `updateInstalledStickerSets` (custom emoji), no refetch goes out, and the new set never shows in the media panel, the suggestion strip or "Add to Emoji Set" until restart (S4). Fix: `let installed_wanted = was_asking || !self.session.stickers.emoji.lists.installed.is_idle() || self.session.stickers.emoji.open;`. `cancel()` has already turned an in-flight ask that held no data into `Idle`, and `was_asking` covers that case. Test: answer the custom-emoji `getInstalledStickerSets` with `"sets":[]`, feed `updateInstalledStickerSets` with `stickerTypeCustomEmoji` while the panel is closed, and assert that a second custom-emoji `getInstalledStickerSets` went out.

- Round-2 item 4 (emoji lists as Fetch): no test fails if src/connect/media_library.rs:36-37 or src/connect/message_menu.rs:724-725 go back to `installed_sets.is_empty()`. The existing `opening_the_panel_requests_both_set_lists_recent_and_favorites_once` opens twice before any answer, so the `is_loading` busy check hides the difference. Fix: in src/connect/tests/media_library.rs, call `open_media_panel`, answer the custom-emoji list with `"sets":[]`, call `open_media_panel` again, then `fetch_sticker_menu_facts`, and assert exactly one custom-emoji `getInstalledStickerSets` was sent.

- Round-2 item 1 (community create), src/ui/communities/create.rs:170-176. The new busy note (`Q_COMMUNITY_CREATE_BUSY`) has no test. Taking it out leaves the press silent again, and nothing fails. Fix: add a flow test in src/ui/communities/flow_tests.rs. With a create that has a picture out (`Creating { photo: Some(_) }`), press Create in a second identity box for another chat, and assert that the status note is `tr(keys::Q_COMMUNITY_CREATE_BUSY)` and that only one `createCommunity` was sent. Also, src/connect/communities.rs:103-106 repeats the `matches!` from `community_photo_create_out` (groups/community.rs:15-20). Use `if self.community_photo_create_out() { return Ok(None); }` so the two cannot drift apart.

- English literals left in bundle files (same class as round-2 item 11, missed by it):
  - src/connect/business_extra.rs:88 `"The chat links request was not sent."` and :203 `"The chatbot request was not sent."`. Fix: `if let Err(err) = &sent { ….fail(err.stage_line()); }`.
  - src/connect/gift_manage.rs:635-640 (`ask_premium_gift_options`): `GiftListFetch::Failed("Couldn't load the Premium options.".into())`. Fix it the same way as `ask_available_gifts` just above: `if let Err(err) = self.send_json_request(..) { …premium_fetch = GiftListFetch::Failed(err.stage_line()); }`.
  - src/connect/groups/group_type.rs:301 `"the group was upgraded, but its link could not be saved"`, pushed to `chat_action_error`. Fix: add a `qll_` key to lang/en (for example in the groups strings file) and push `crate::lang::tr(keys::…).to_string()`.
