## Failures from this round's changes

- **Regression: a camera or microphone prompt shown during a recording is ignored.** `src/ui/recording_state.rs` `RecordingUi::begin_asking` (about line 150) now refuses to replace a `Recording`. `with_device_access` (`src/ui/capture_access.rs:166-227`) checks only `recording.starting()`, then calls `request(device, sender)` (the OS prompt) before `begin_asking` drops the wait task. Before this round `CaptureStart::Asking` sat beside the capture, so this worked. Trigger: a voice recording runs, and a call's camera (`with_camera_access`) is turned on for the first time (access Undetermined). The system prompt appears with "Allow camera". The user allows, nothing happens, and they have to press again. Fix: in the Undetermined branch, check `self.recording.busy()` instead of `starting()` before calling `request(..)`, and show `Q_MISC_FINISH_THE_RECORDING_FIRST`. That way no prompt is shown when nobody waits for its answer. Also fix the comment there ("starting or running"). If the call camera must keep working during a recording, keep its Asking stage outside `RecordStage`. The test `a_start_cannot_replace_or_cancel_a_running_recording` (`recording_start_tests.rs:290`) should also cover this case through `with_device_access`.

- **21-007 is still open for a file attached twice.** `src/ui/send_card/tiles.rs:470-476` / `still_at` (843) accept the index when the same path is there. Photos can be attached twice (`ComposerAttachment::push_attachment` does not deduplicate). Trigger: tray `[a, b, b']`, where b' is the same photo again. Another window removes `a`. A click on the tile drawn for `b` (index 1) now toggles the spoiler, edits or removes `b'`. The new test asserts exactly this case as correct (`assert!(still_at(&tray, 1, Path::new(&b)))` after `tray.remove(0)`). Fix: give each attachment an identity when it joins the tray, for example a `u64` id on `ComposerAttachment` assigned in `push_attachment`. `TrayItem` holds that id, and `tray_index_of` finds the entry by id. Update the test so the shifted twin is refused.

## Findings the final re-read would record in bundle files (older than this round; the first review missed them)

- **S3 (confirmed), `src/ui/selection_drag.rs:392-397` `message_still_sending`.** It looks only in `session.histories[chat]`. Topic pages go only into `threads.topic_histories` (`state/topic_window.rs:156-200`), so for a topic row it returns `pending = true`, and `ForwardDraft::toggle` returns early. Trigger: open a forum topic, Select a message from the menu, then click other rows. Nothing toggles. Fix: look the message up where the view reads it. Add a `Session::shown_message(chat, topic, id)` that checks the open topic's `topic_histories`, the open thread, then `histories`, like `reply_target` in `state/composer_targets.rs`, and use it here.

- **S2 when main history is loaded (plausible), S3 when it is empty (confirmed): `src/ui/selection_mode.rs:299` `loaded_selectable_ids`, used by `selection_drag.rs:120, 276-283, 384`.** Range ids come from the chat's main history, not from what the topic view shows. If the main history is empty, a drag over topic rows shows a preview, and the release selects nothing ("Forward 0"). If the main history is loaded, the release adds messages from *other topics* whose ids fall in the range, and Delete or Forward acts on messages the user never saw. Fix: `loaded_selectable_ids(chat, open topic or thread)` reads the history the view draws. `select_up_to`, `can_select_up_to` and `shortcut_pack.rs:364/486` use the same helper.

- **S3 (confirmed), `src/ui/selectable_text.rs:734-772` with `entity_links.rs:472-507`.** `chat_ui.link_tooltip` is cleared only by the hovered element's own mouse-move listener, or by a click or menu. Trigger: hover a link until its tooltip shows, wheel-scroll it out of the list (a wheel sends no mouse move), then move the mouse. The tooltip stays at the old spot over other messages. Fix: clear `link_tooltip` on a history scroll and on mouse exit or window deactivate. In `SelectableRichText::paint`, if `over` is `Some` but the hitbox is no longer hovered, call the handler with `None`.

- **S3 (confirmed), `src/ui/polls/mod.rs:271`, caused by `src/state/session_forward.rs:44-51`.** `updatePoll` removes every `poll_voters` entry of the message, including the one the open dialog shows and a page in flight. The open dialog then shows "Select an option to see voters" with the option still highlighted, and nothing asks again. On a busy poll this happens on every vote. Fix: mark the entry stale instead of removing it (`PollVotersFetch::Stale`, or `VotersMore::Stale`). Have the dialog's upkeep refetch the stale key it shows through `fetch_poll_voters`. A failed send writes `Failed`, so the upkeep cannot loop.

- **S4 (confirmed), `src/ui/polls/mod.rs:377-379`.** The stats Retry calls `open_poll_stats_dialog`. That rebuilds the dialog (`PollView::Stats { option: None }`), drops the user's chosen option and fetches option 0 again. Fix: add `retry_poll_stats` that only resends `fetch_poll_vote_statistics` and keeps the dialog.

- **S3 (confirmed), `src/ui/premium_ui/grams.rs:359-373`.** A failed first `getTonTransactions` page leaves no rows and no tabs, and `has_more()` is false. The error text is drawn with no Retry (the `PageLoad::Failed` doc says "drawn with a Retry"), and `grams_more` cannot retry. Closing the box is the only way out. - **IS (confirmed), `src/ui/premium_ui/grams.rs:140-181`, fields `GramsHub::open` and `GramsHub::selected` (`premium_hub/ton.rs:539`).** The box being open and the receipt being shown are two fields kept in step by hand. `select_grams_tx` writes `selected` without checking `open`, and `open_grams` (demo) sets `open = true` by hand.
