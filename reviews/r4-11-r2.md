## Failures

- **22-006 is still not fully fixed: in several held states the tick never rests.** `src/ui/story_viewer/tick_rest.rs:80-91`. `story_tick_rests` treats a held story as "waiting" in states where nothing is out. In those states the tick keeps waking every 100 ms. Each wake runs `sync_story_video`, `tick_close_friends`, `live_story_tick` and `warm_story_custom_emoji`. It does not redraw. This is the "work while hidden" the entry is about. Triggers:
  1. Close friends panel with no load out. `CloseFriendsStage::Awaiting` counts as waiting whatever the session's list is doing. With `CloseFriendsList::Failed { stale: None }` (the load failed and the panel shows Retry) or `NotLoaded`, nothing will ever arrive. The tick runs for as long as the panel is open, also with the window in the background. The new test encodes this as intended: `tick_rest_tests.rs:41-55` sets `NotLoaded` and asserts "the panel waits on the list: the tick stays".
  2. Custom emoji that never resolve. `story_custom_emoji_warming` (`tick_rest.rs:103-124`) returns true for any id whose sticker is unknown (`None => true`) or whose file is not local. A reaction custom emoji that `getCustomEmojiStickers` does not return, one whose fetch keeps failing, one whose file cannot be downloaded, or any custom emoji in a demo session (no driver) keeps the tick going forever.
  3. A live target that is not being joined. The `live_story_target().is_none()` condition keeps the tick going on a refused live story (`LiveJoin::Refused`, which `sync_live_story` does not join again). It also keeps it going while a live PiP plays and the viewer is held on an ordinary story. In the PiP case `watching()` is `Some`, so `still` is false and the held overlay is also redrawn every 100 ms.

  Fix: count only what is really out.
  - Close friends: `Saving { .. }`, or `Awaiting` while `session.stories.close_friends` is `Loading`. The Retry press already redraws the app, so `wake_story_tick_if_due` restarts the tick when the load is out again.
  - Custom emoji: a fetch out (`custom_emoji_fetch` in flight) or a display file with `is_downloading_active()` / `downloads.is_requested`. Not "not local yet". The backoff retry then runs from resume or redraw, not from a 100 ms poll.
  - Live: `watching().is_some()`, or `live_story_target()` is `Some` and differs from `refused()` (a join is due). For the PiP case, the shown item, not the PiP, decides whether the held overlay moves.
  - Change the first test so that a `NotLoaded`/`Failed` list rests and a `Loading` list keeps the tick. Add a test that a held story with an unresolvable custom emoji rests.

- **Two timer tasks re-arm themselves on a fixed period.** A sibling bundle is extending `check-owned-timers.py` to reject this shape, and both will trip it:
  - `src/ui/story_viewer/mod.rs:811-836` (`story_tick_task`): a 100 ms `timer(...)`, then `Wake::Goes` spawns the next one (`:828-833`). While a story plays this is the progress clock (tdesktop `kPhotoProgressInterval`). The shape is still "poll every 100 ms". To make it pass the new rule without an allow line:
    - Draw the progress bar on the frame clock (`request_animation_tick` while playing and visible).
    - Arm one deadline task for `story_segment_finished` (the segment's remaining time from `playback`).
    - Let the other polled things end from their own events: the session update for close friends and custom emoji, the live tracker for live stories, the native player's callbacks for video.

    If the owner keeps the clock, the honest form is an allow line naming it as the visible progress clock. It is held by `StoryTick::Running` and ends on `Rests`/`Closed`. That is an owner decision, since this round adds no allow lines.
  - `src/ui/story_stealth_ui.rs:243-263` (`stealth_box_tick`): it re-arms every whole second for as long as the box is open, and every wake calls a full `cx.notify()`. It also does this when the button shows no countdown (`StealthButton` not `Cooldown`/active, for example a non-Premium user's "Unlock" or a fresh "Enable"). Then the redraw changes nothing.

    Fix: derive the next change from the facts the box shows. While a countdown is visible, wait until the next whole second of that countdown, and end at its `until`. With no countdown, hold `Upkeep::Idle`-style nothing and let the activation answer or a mode update redraw. If the per-second countdown stays, it needs the same owner-approved allow line as a visible clock.

- **A clip whose open lands after `OPEN_GIVE_UP` is never redrawn.** `src/ui/sticker_player/app.rs:416-436` and `mod.rs:428-456`. The previous fix stopped failing the clip, which is right. But the engine's wake for an open (`opener.rs:35`, `worker.rs:49`: "a clip opened or failed") reaches the pump, and the pump only notifies when `drain()` returns true. `drain()` is true only when a first rendered frame arrived, and no frame is rendered until a view's `frame()` calls `ask`.

  Until the give-up, the views' 30 fps opening ticks call `frame()`. After it, `fps()` returns 0 and `changes_in` returns false (`view.rs:139`, `:174`). So when a slow open lands, nothing redraws. Nothing asks for frame 0. The view shows its still until an unrelated redraw.

  Trigger: a chat with hundreds of animated custom emoji on a slow machine, where an open queues past 30 s. Once the user stops interacting, those emoji stay still even though their clips are open. Before this bundle they kept ticking and played on open.

  The new test `a_clip_that_opens_after_the_give_up_still_plays` (`tests.rs:692-725`) calls `frame()` by hand, so it does not cover this. The pump is also off under `cfg(test)`.

  Fix: have the pump redraw on an open or fail wake. For example, `Player::settle_opens()` moves every `Opening::Pending` clip to `Ready`/`Failed` from `engine.state` and returns whether any moved, and the pump does `if drain() || settle_opens() { cx.notify() }`. Then the views do not need to poll at 30 fps while a clip opens at all. Also fix the stale comment at `view.rs:138` ("An open that outlived its give-up is a failed one"): it is not failed any more.

- **22-003: the wait has no exit when no transfer was started, and the variant was renamed off the guard's word list.**
  - Exit gap, `src/ui/sticker_set_box/video_pick.rs:62-73` with `video_create.rs:85-117`. `ask_pick_file` treats `download_file(..) == Ok(None)` as "asked", but `send_auto_download` returns `Ok(None)` without sending anything in these cases (`connect/media.rs:263-268`, `session_files.rs:155-180`):
    - the file `!can_be_downloaded()`;
    - a user cancel of that file is still settling (`is_cancelling`);
    - TDLib already runs an untracked transfer of it.

    In each case the tracker holds no record, or one that is later removed (`confirm_cancel`), or one that never reaches `Phase::Ended` (an untracked transfer going idle is not `end`ed, because `is_requested` is false). So `ended_without_file` never turns true, and `PickWait::FileWanted` holds until the user closes the box or picks again.

    Fix: in `settle_sticker_pick_download`, also end the wait with the note when the file is not local, `!local.is_downloading_active()`, and nothing of ours is out for it (`!downloads.is_requested(id) && !requests.has_download(id)`). Alternatively, have the pick use a user-intent download (`download_user_file`, which undoes a pending cancel and always records the transfer). Add a test for a pick whose `download_file` sends nothing.
  - Rename, `src/ui/sticker_set_box/state.rs:440`. `PickWait::Downloading` became `FileWanted`. That moves it off `IN_FLIGHT` in `check-stage-enums.py` (the baseline line `unkeyed:PickWait::Downloading` went away with it). The variant is a real in-flight stage: it waits on a `downloadFile` transfer Quill asked for, keyed by `pending.file_id`. The decision doc row still calls it `PickWait::Downloading(pending)` (`docs/decisions/account-scoped-ui-state.md`, r4-11 table, 22-003 row), so code and doc disagree.

    Fix, owner's choice: keep the honest name `Downloading` and add a `stage-enums-allow.txt` line with the reason (it waits on TDLib's transfer of `pending.file_id`; `settle_sticker_pick_download` ends it from the tracker's end), or teach the guard that a download stage keyed by its `FileId` holds what ends it. Either way, make the doc row match the code.
