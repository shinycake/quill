- **Regression: a membership change now deletes member lists that are loading for the first time or failed, and nothing asks for them again.** `SupergroupMembersFetch::made_stale` returns `None` for `Loading { last: None }`, `Failed` and `NotSent` (src/state/member_fetch_types.rs:86). So `GroupsState::members_changed` removes those entries (src/state/domains/groups/member_lists.rs:43-61), and the same happens to `basic_group_members`.
  - On the base branch the request stayed recorded in `member_asks`, so the answer still landed. The poll also asked again for every list of the changed chat.
  - Now the answer of the request already in flight finds no list and is dropped (`answer_member_first`, member_lists.rs:159; `basic_members_wait_for`). The poll asks again only for `Stale` lists (src/ui/notifications/poll_drains.rs:202-206).
  - Result: the member dialog shows "Loading members…" for a missing entry (src/ui/group_members.rs:349), and the inline panel shows Loading with no Retry (src/ui/inline_members_view.rs:234). Both stay that way with nothing in flight.
  - Trigger: the inline member list fails and shows Retry. The user adds someone through the header's "Add members". `AddChatMembers` succeeds, `members_changed` runs, and the Retry becomes a spinner that never ends.
  - Fix: leave `Failed`/`NotSent` as they are (they already draw Retry). Turn `Loading { last: None }` into a `Stale` stage without a page (for example `Stale { last: Option<MembersPage> }`), so the poll and the next reader ask again. Do the same for basic groups. Add a test: a failed list and a list on its first load go through `members_changed`, and the panel asks again or shows Retry.

- **The poll checks one list but refreshes another, so it can repeat a no-op refresh on every pass.** `member_dialog_is_stale` uses `member_dialog_filter`, which maps the Restricted and Banned tabs to `Recent` when the viewer has no restrict right (src/ui/group_members.rs:625-660, fallback at :656). `refresh_member_dialog` asks for `tab.filter()` instead (src/ui/group_members.rs:116).
  - Without the right, `send_supergroup_members` drops the stale Banned key and returns `Ok(None)` (src/connect/moderation/members.rs:44).
  - The `Recent` key stays `Stale`, so every poll calls the refresh again and sets `progressed`, which forces an immediate redraw (`RedrawNeed::Now`) each time.
  - Trigger: open the dialog on All (this loads Recent), switch to Banned, then get demoted. The demotion runs `members_changed`.
  - Fix: refresh exactly the key the dialog shows. Either build the request in `refresh_member_dialog` from `member_dialog_filter`, or have the poll refresh the stale key it found. Add a test.

- **The new `ticket` guard misses purpose enums in files without "purpose" in the path.** scripts/check-request-match.py:84 scans only files under `src/state/` whose path contains "purpose".
  - `AiComposePurpose` is defined in src/state/domains/messages/ai_compose.rs. Putting back the `BoxCompose { token: u64 }` that 08-008 removed would pass CI.
  - The guard also does not report an existing hit: `LocationPickerPurpose::SearchVenues { generation: u64 }` at src/location_picker/mod.rs:31. About a dozen other `*Purpose` enums outside such files are not scanned either (earn, passkeys, gift_market, settings/language, stickers/creator, stories/live, …).
  - Fix: scan the body of every `enum \w*Purpose` anywhere under `src/`, baseline the location-picker hit, and add a `test_shape_guard.py` case with a purpose enum in a file whose name does not contain "purpose".
