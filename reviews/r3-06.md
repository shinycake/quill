# Review of r3-06 (Opus, 2026-11-12). Verdict: merge after these fixes

Line numbers are on origin/claude/sweep-r3-06.

- **The new `generation` guard misses the shape it was written for.** `scripts/check-request-match.py:64-77` sets `variant` when `VARIANT` matches a line and only tests `GENERATION_FIELD` on the lines after it (`elif`). `GENERATION_FIELD` is also anchored at line start (`^\s+generation`). A one-line purpose variant such as `    DeepLinkInfo { generation: u64 },` therefore never hits. That is exactly how all five `ChatsPurpose::DeepLink*` variants were written on the base (`src/state/domains/chats/purpose.rs:11,15,20,22,25` on origin/claude/sweep-r3). Running the rule's regexes over that base file gives zero hits. So the guard would not have caught 10-001 and will not catch it coming back. Fix: when `VARIANT` matches, also search the rest of that line for `\bgeneration\s*:\s*u64\b` (for example `re.search(r"\{[^}]*\bgeneration\s*:\s*u64\b", line)`) and yield `generation:<Variant>` on that line. Keep the multi-line check. Add a self-test, or a fixture string in the script's test, that feeds it the old one-line `DeepLinkInfo { generation: u64 },` and expects a hit.

- **09-013: a phone-share answer that has no owner stays in the queue for good.** `WebApps::phone_share` is now a `Vec`. The apply arms push to it (`src/state/domains/messages/apply.rs:560-564`, `src/state/session_web_apps.rs:265-269`), but only `poll_phone` removes an entry, and only the one for the window's current `PhoneFlow::Sending { request }` (`src/ui/web_app_ui/phone.rs:232-241`). `finish_phone` clears only an entry that is already there (`phone.rs:191-200`). Two cases never get cleaned up:
  - An answer that lands after a timed-out send. The comment at `phone.rs:189` says this answer "is nobody's".
  - The answer to a send whose mini-app window closed while Sending. `spawn_mini_app_window.rs:155-158` forgets only the ack.

  Both entries stay until the account is reset. The old `Option` was overwritten by the next answer and cleared at the next send, so this is a new leak with no way out. Fix: drain `phone_share` in `poll_mini_app_session` with `std::mem::take`, as `write_access` is drained at `spawn_mini_app_window.rs:206`. Pass the entry for the window's `Sending` request to the phone flow and drop the rest. Alternatively, make the close paths (`spawn_mini_app_window.rs:155`, `:182`) and the late-answer case drop the entry by its request. Extend `connect/tests/web_apps.rs` with a case where the answer arrives after the flow ended and the queue ends up empty.
