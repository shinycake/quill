## Failures

- **src/ui/notifications/photo_preview.rs:126 (g-332 / 19-002). S3 bug, confirmed.**
  - **What is wrong:** `settle_preview_wait` calls `_deadline.detach()`. When the poll shows a wait early because its photo landed, the deadline task keeps running. After `PHOTO_WAIT` it calls `settle_preview_wait(&key)` on whatever entry holds that `(account, chat)` key at that point. The bundle removed the id counter that used to stop exactly this, and the guard cannot see a `.detach()` on a variable.
  - **Trigger:**
    1. A photo message from chat A waits for its photo (t=0).
    2. The photo lands at t=0.5 and the poll shows the notification.
    3. A second photo message from A arrives at t=1, so a new wait starts.
    4. At t=3 the first task settles the second wait: it shows without its photo, 2 s early.
  - **Fix:** drop the task instead of detaching it (`drop(_deadline)`, or destructure with `..`). Dropping a task from inside its own update is safe, and this bundle already does it in `arm_notify_clock`. Add a test: settle early, insert a new wait for the same chat, advance the manual clock past `PHOTO_WAIT`, and check the new wait is still pending.

  - **Fix, step 1: extend `scripts/check-owned-timers.py`.** Flag a function that spawns a task whose body awaits a constant-duration timer and calls the same function again from its update. Also scan the bodies of helpers like `sleep_or_wake_paced`.

- **src/ui/location_picker/mod.rs:79-91 (`poll_answer_unless`, g-383). S3 regression, confirmed.**
  - **What is wrong:** the old `WaitBudget` did not count time while the permission prompt was open. The new code restarts the 30 s only if the prompt is still open at the moment the timer fires, so time the user spent on the prompt counts once it closes.
  - **Trigger (macOS first use):**
    1. Open Send Location.
    2. Read the "Allow location" prompt for 25 s, then Allow.
    3. The fix takes more than 5 s, and the picker shows "location unavailable".
  - The module doc still promises the opposite.
  - **Fix:** restart the full limit when the prompt closes. One way: race against a third future that the delegate wakes when the prompt closes. Another: an epoch the delegate bumps, with `poll_answer_unless` restarting the limit whenever the epoch moved during the race. Add a manual-clock test: prompt open 25 s, answer at 32 s, and the answer lands.
