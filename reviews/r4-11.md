## Failures

- **22-006 is only half fixed, and the fix causes a regression.** `src/ui/story_viewer/mod.rs:833-855`. The tick still wakes every 100 ms while the viewer is open, including when it is paused, behind a panel, or in an inactive or minimized window. On each wake it runs `sync_story_video`, `tick_close_friends`, `live_story_tick` and `warm_story_custom_emoji`. Only the redraw stopped, so the "work while hidden" part of the entry is still there.

  The new `still` rule also drops redraws that some state changes need. `tick_close_friends` (`story_more.rs:579-654`) is the only thing that moves the close-friends panel's stage, and it does not notify. The panel is open, which counts as paused, so the wake no longer notifies either.

  Trigger: open a story, choose ⋯ → Close friends, and let the list arrive. The poll loop's redraw still shows Awaiting ("Loading…"). The next wake moves the stage to Editing with no redraw, so "Loading…" stays until something else redraws. A failed save (`Saving` → `Editing`, line 607-611) has the same problem. A stealth toast shown while the viewer is paused with Space also outlives its 4 s, because its `until` is only checked at render.

  Fix: have `tick_close_friends` return whether it changed the stage (or call `notify_story` itself when it does), and notify on that. Count a showing stealth toast as a change until its `until` has passed. Then do what the entry asked: when `still` and nothing is pending, end the tick (`StoryTick::Off`, no next task) instead of re-arming it. Start it again from what resumes playback (`refresh_story_pause` already calls `ensure_story_tick`; the Space toggle and window activation need to as well). Add a test: close-friends list arrives while the panel is open → the panel shows the list without any other input.

- **Regression: a slow clip open now fails for good while it is on screen.** `src/ui/sticker_player/mod.rs:518-520`. Once `OPEN_GIVE_UP` (30 s) has passed, the `Some(ClipState::Opening) if open_gave_up(..)` arm writes `Opening::Failed` into the `UiClip`. Nothing reads the engine again after that. Line 514 only checks `Pending`, and `close_stale` never closes a clip that is still drawn.

  The engine already guarantees an answer: `worker_ended` and `opener_ended` fail their clips, and `worker.rs:49` / `opener.rs:35` wake the UI on open or fail. So 30 s only means "busy". Trigger: a chat or pack with a few hundred animated custom emoji on a slow machine. Opens queue behind frames (`FRAMES_BEFORE_OPEN`), and any clip that takes longer than 30 s shows its still for as long as it stays on screen, even though the engine has opened it. Before this bundle it played as soon as it opened.

  Fix: delete the arm at 518-520 so the clip stays `Pending` and the engine's wake installs `Ready`. The view-side give-up in `view.rs:139` and `:174` already stops the ticks, which is all the test needs. The `since` in `Opening::Pending` then stays as the deadline that ends the view's ticks, which is accurate.

- **22-003 (confirmed) is not fixed. It is reframed, and the guard is satisfied by a deadline.** `src/ui/sticker_set_box/state.rs:410-449`, `video_create.rs:107-125`. The entry says the wait is "ended by polling the download tracker each frame" and that a host window that draws no frame keeps it. Both are still true. The bundle added `Instant` and a 3-minute give-up, which is what makes `unkeyed:PickWait::Downloading` pass (`Instant` is a carrier in `check-stage-enums.py`). The decision doc then calls the remaining behaviour intended. Round 4 allows a confirmed entry to be skipped only with a test that proves the trigger has no effect. Here the effect happens by design.

  The give-up also adds a small regression. A large GIF ("Adapt from a Sticker" on a GIF) still downloading after 3 minutes on a slow link is dropped with "Could not download", while the download keeps running.

  Fix, as the entry proposed: end the wait from the download's own end. On the file update that completes `file_id` (or `ended_without_file`), move the stage to `PickWait::Downloaded { pending, path }`, or end it with the note. That happens in the session update path, not in a frame. The host window's frame then only opens the editor from `Downloaded`, because the editor has to open in that window. The deadline can go. If the owner accepts the current design, record it as an accepted skip in section 8 with that reason, so the final sweep does not report it again.

- **Redraw loop while a story-page call is out.** `src/ui/story_albums/page_wait.rs:61`. The early return only fires when both `delete_answer` and `answered` are `None`. While a create, save or delete call is still out they are `Some(None)`, so the function goes on to `cx.notify()` at line 111. `story_page_upkeep` runs in the main window's render (`frame_upkeep.rs:58`), so every frame asks for the next one, for as long as the call is out. With the network down that lasts until TDLib answers. This is older than the bundle, but this file is in it. The `Option<Option<Answer>>` reshape for g-287 was the moment to see it.

  Fix: `if delete_answer.flatten().is_none() && answered.flatten().is_none() { return; }`. Add a test that a frame with the call still `Sending` does not notify.

- **Placeholder stage in the GPU-loss watcher.** `src/ui/startup_failure/device_loss.rs:87-122`. `recover()` writes `Recovered { reopen: Reopen::NotStarted }`, and the caller then overwrites it from outside through `hold_reopen`. `NotStarted` is never a real stage on the success path, and it stays forever on the give-up path. A re-reader will record a two-step transition with a placeholder variant (IS).

  Fix: make it one call, for example `fn recover(&mut self, start: impl FnOnce(KeptWindow) -> Task<()>) -> bool`. When a window was kept, it sets `Recovered { kept: None, _reopen: start(left) }` and returns true. Otherwise it returns false and leaves a `Recovered { kept: None, .. }` that holds no task (the caller quits). Drop `Reopen` and `hold_reopen`.

- **A stage name that is not accurate.** `src/ui/statistics_export.rs:198-199`. `StatsExport::Choosing` also covers the write after the save dialog answers ("Choosing the file, then writing it"). Rename it to `Exporting { _task }`. `Exporting` is an in-flight word and the variant holds its `Task`, so the guard still passes.

- **The doc comment contradicts the code.** `src/ui/story_viewer/live_state.rs:146-148`. `LiveJoin::Offline` says "no call is ever seen", but `mark_call_seen` (line 208) moves `Offline` to `Joined`, and `live_tests.rs:926-927` depend on it. Fix the comment: "nothing is out, so nothing can fail; a call the demo feeds is still seen". The variant itself is fine. It waits on nothing Quill started, and the name is accurate.

## Checked and fine

- **22-004:** the grace wake lives in `Pointer::Leaving` and drops with every stage change. `Peek` is a `Copy` view of it.
- **22-007:** temp names are unique per call, and the threaded test covers it. Refusing a new download while `Cancelling` was the other option, and the per-call name is the smaller change.
- **g-301:** the progress loop waits on `Progress::changed`, poked by each chunk and by `finish`. `FinishOnDrop` guarantees `finish` runs even on a panic, so the loop always ends. `cancel` does not poke, which is correct.
- **22-001:** `EngineBuild::Building { _task }` is a real stage, and the install is its own exit.
- **22-002:** `TileState::Failed` is caught by `catch_unwind`, and the trim takes it back to `Idle`.
- **RefCell lines g-304..g-321:** all are `try_borrow*` or `Cell::take`.
- **g-295/g-296:** the reopen task is held for the app's life. It is never overwritten, because `recover` is reachable only from `Healthy`. The `on_window_closed` subscription's `.detach()` is a subscription, not a timer.
- **22-005:** `ChartFocus` is one value. `step` does nothing in a pie.
- **22-008:** `StatsExport` lives in the account's `DialogUi`, which is replaced with the screen. Cancel, write and account-leave all end the stage, and the test covers a second press.
- **g-297:** the sticker closer waits on the next frame or a deadline, not a fixed clock. The one-wait-per-task form behaves the same.
- **g-302:** the stealth box's per-second redraw is a visible countdown clock, owned by the box and dropped with it. The respawn form is equivalent to the old loop. Note that `check-owned-timers.py` cannot see a task that re-arms itself after a `.timer(` await (this shape, and `story_tick_task`). A later round should teach it that shape.
- **g-290:** `ListView` is derived each frame and holds nothing, so the name is accurate. The masks loading check reads the `Fetch` stages.
- **g-280..g-285:** `StickerPanel::changing` maps a set to the `RequestId` that changes it. It is cleared by the matching answer or error (`session_apply_ok.rs:351`, `error.rs:126`). A request that leaves with no answer leaves a stale entry, but `sticker_set_change_pending` checks the request table, so it reads as not pending. `cancel_sticker_suggestions` drops the request held by `SuggestFor::Asked`.
- **g-287:** `Answer` is a derived result, and `Option` for "still out" is accurate.
- **g-293:** `Joining` always holds its request.
- **new-01:** `SetEditing::Choosing` and `Writing` hold their tasks. Another flow drops them, and a dropped write never lands.
- **g-291/g-292 data shape:** fine, apart from the regression above.
