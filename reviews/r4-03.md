## Failures

### Bundle ids not fully fixed

1. **04-005: answers still matched by a counter (src/connect/settings/mod.rs:176-206, src/state/domains/settings/state.rs:530-547).**
   - The decision doc says the blocked page "holds its request". Nothing reads that request.
   - Answers and errors are still matched by `blocked_generation` in `SettingsPurpose::GetBlockedSenders`, and `apply_blocked_page` settles the list with the unmatched `succeed`. The baseline still has `counter:SettingsPurpose::GetBlockedSenders 1` and `unmatched:SettingsState::apply_blocked_page 2`.
   - An unblock or block that fails to send calls `blocked_senders.fail` (mod.rs:229, :262). That ends a page in flight without changing the generation. The next scroll then sends a second page under the same generation, and the first page's answer or error lands on it.
   - Fix: make the list `Fetch<BlockedList { ids, total }>` and settle it with `answered(Some(pending.id), ..)` / `failed(Some(id), ..)`. Delete `blocked_generation`, `restart_blocked_list` and the purpose's `generation`, and drop both baseline lines. This also folds `blocked_total` into the stage: today unblock, block and `apply_blocked_page` each write it by hand beside the list, and `fail_dropping_data` drops the ids but keeps the total.

2. **04-005: new regressions from the refresh on every open (src/connect/settings/mod.rs:235-239, :268-276, :179).**
   - (a) S3. The page-0 refresh now runs while the old list is on screen with live Unblock buttons.
     - Trigger: open Privacy, then Unblock X before page 0 answers (or Block from a chat menu while the refresh is out).
     - The optimistic `retain`/`push` does not drop the page in flight. Page 0 was asked before the change, and it replaces the list.
     - Effect: X shows as blocked again and the total is wrong until the next open.
     - Fix: when the list is loading, a block or unblock replaces the stage and asks page 0 again after its `ok`.
   - (b) S4. `ask_blocked_page(0)` returns `Ok(())` while a next-page fetch is out ("one page at a time").
     - Trigger: scroll so a next page is out, then reopen Privacy. The refresh is silently skipped.
     - Fix: an offset-0 ask replaces a page in flight. It sends a new request, and the older page no longer matches.
   - (c) S4, plausible. `privacy.blocked_asked` (`scroll_load::Asked`, ui/privacy/mod.rs:388) is never reset when the list restarts.
     - Effect: after page 0 refills to the same length, the next page waits for a scroll.
     - Fix: reset it when a page-0 refresh is sent.

4. **04-007 and 04-011: the skip reason does not hold (src/connect/sticker_manager.rs:12, src/connect/stickers.rs:131).**

### Bundle changes that broke behaviour or left the shape

5. **Saved GIFs answer still matched by purpose (src/connect/stickers.rs:783 with src/state/sticker_gif_types.rs:584, :607, :642). S3, regression.**

   - Trigger: getSavedAnimations #1 is out. A saved GIF is removed (session_apply_ok.rs:389) or `show_saved_gifs` runs. #2 goes out.
   - Effect: #1's answer, which predates the change, lands as Ready and the removed GIF reappears. An error on #1 fails the list while #2 is out.
   - Fix: pass `pending.map(|p| p.id)` through `accept_saved_animations`, and settle with `saved.answered(request, ())` / `saved.failed(request, ..)`.

6. **`emoji_set_request` still dedupes by `has_purpose` after its `take_purpose` drops were removed (src/connect/sticker_creator.rs:241-246, src/emoji/mod.rs:753-755; sender in src/connect/emoji_sets.rs). S4.**

   - Fix: gate list purposes on `lists.for_purpose(purpose).is_loading()`, the same as `sticker_request`, and keep `has_purpose` only for purposes without a list.

7. **Two sticker reorders can be out at once (src/connect/stickers.rs:222-229, src/connect/sticker_manager.rs:160, `StickerChanges::reorder: Option<RequestId>`). S4.**
