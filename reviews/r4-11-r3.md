## Failures

- **The `FileId` carrier loosens `check-stage-enums.py` for unrelated enums.** `scripts/check-stage-enums.py:80` adds `FileId` to `CARRIER`. `carries()` applies `CARRIER` to every in-flight variant name (`Waiting`, `Sending`, `Loading`, …) and to every type the variant names, up to 3 levels deep. Any in-flight variant whose data contains a `FileId` anywhere now counts as holding what ends it, and most message, media and sticker types contain one. I ran the old and new scripts on this tree and diffed `--list`. Besides the intended `PickWait::Downloading`, two other hits disappear:
  - `src/ui/touch_bar/mac/bars.rs:297 unkeyed:PickerFill::Waiting`. This waits for the user's next tap. It holds `PickerContents` → `PickerItem` → `PickerSticker`, which has a `FileId`, so the variant is now hidden, though no download is involved. Its baseline line (`stage-enums-baseline.txt:134`) is now stale.
  - `src/composer/edit_media_tools.rs:49 unkeyed:EditImageFetch::Downloading`. This one really is a download wait, but its allow line (`stage-enums-allow.txt:16`) is now stale.

  `check-stage-enums.py` without flags prints "2 baseline line(s) can go" and still exits 0. `--strict` exits 1. Later, an unkeyed `Sending(OutgoingMedia)` or `Waiting(Message)` would pass without a hit. The self-test only shows that the intended case passes. It does not show that unrelated variants still fail.

  Fix:
  - Count a `FileId` only for a variant named `Downloading`, and only as a direct field of the variant or a direct field of a type the variant names directly (depth 1). For example, a `DOWNLOAD_CARRIER = re.compile(r"\bFileId\b")` checked in `hits()` only when `name == "Downloading"`, against `data` and the bodies of the names in `data`, without recursion. Keep `FileId` out of `CARRIER`.
  - Extend `test_a_download_stage_holds_its_file_id` with variants that must still fail: `Waiting(Contents)` where `Contents` nests a `FileId`, and `Sending { file: FileId }`.
  - Then `PickerFill::Waiting` is reported again under its existing baseline line. `EditImageFetch::Downloading` passes, and its allow line becomes stale. Remove it, which is a removal and so allowed.

## Checked and fine

The story viewer's frame upkeep notifies only when something moved (`tick_close_friends`, step, toast end) or while the overlay moves. Its other calls notify only on events, so there is no redraw loop. While Quill is behind another app, the clock asks nothing. Nothing is lost there: live-story Stars are committed by the driver's own `poll_ticks` (`live_story_reaction_tick`), and a live PiP's end is checked by `check_live_pip` at each root render. The upkeep is skipped while locked, and the story is held then anyway. Closing the viewer stops playback and clears `emoji_warm` in the upkeep. The stealth box's 1 fps tick redraws the whole app, because a dialog draws outside any slice. That is the same cost the old once-a-second `cx.notify()` had, and it runs only while a countdown shows. `notify_story_slice` notifies only the overlay slice. `settle_opens` is O(clips) per pump wake but matches `Pending` before asking the engine. Since `prepare`/`frame` open the clip in the engine synchronously, a `None` state never meets a fresh `Pending`. Every round-3 test uses frames and `advance_clock`, with no sleeps.
