## Failures

1. **src/ui/updates.rs:56-75. Regression, S4, confirmed by reading.**
   - What is wrong: from `DownloadFailed`, the timer now calls `check_for_updates`, which sets `Checking`, a state with no release. The usual reason a download fails is being offline. The check then also fails, so `apply_check_result` sets `UpdateState::Failed("Release server unavailable…")`. The kept release is gone:
     - `known_release()` is `None`, so the release notes, "View release on GitHub" and the Update button go.
     - The title-bar pill shows no update to act on.
     - Nothing comes back until a later 4-hour check succeeds.

     The doc comment above the function still says the timer never replaces a failed update with "a check that may fail offline (`Checking` keeps no offer to return to)". The code now does exactly that.
   - Fix: let the timer's check from `DownloadFailed(release, _)` keep that release as a fallback. For example, `check_for_updates_keeping(Some(release))` with the fallback moved into the spawned task, mapping a `Failed(_)` result to `DownloadFailed(release, message)` before `apply_check_result`. `Available`, `UpToDate` and `NoRelease` results apply as now. Then fix the doc comment.
   - Test, on the manual clock:
     1. Hold `FORCE_LOCK`.
     2. Force the check result to `Failed`, by extending the `force_latest_release` seam to force an `UpdateState`.
     3. Start from `DownloadFailed(release, "offline")`, then `advance_clock(RECHECK_EVERY)`.
     4. Assert the state is `DownloadFailed(r, ..)` with the same version.

     Also make `the_timer_finds_a_newer_release_after_a_failed_download` force `force_self_update_available(Some(Err(..)))`. Today its expected `Available` depends on the real self-update answer in the test process: an `Ok` there would auto-download and give `Downloading`.
2. **src/ui/video_player/backend_ffmpeg.rs:398-419. Lost wake, S4, confirmed by reading.**
   - What is wrong: the wake is taken out of the live slot before `open_player`. If the reopen is refused, it is put back with `get_or_insert`. In between, the old player, which stays, may finish its open. Its forwarder then finds the slot empty and fires nothing, and the wake put back afterwards never fires. The clip's open is never redrawn, which is the bug this item exists for.
   - Fix: after putting the wake back on the refused branch, register again with `self.player.on_open(forward_open(&self.open_wake));`. `on_open` runs at once when the old player has already settled. Otherwise it queues a second forwarder, which finds the slot empty after the first one.
   - Test:
     1. Give the reopen seam a refusal, for example `reopen_with: Option<Result<Box<dyn Demuxer>, String>>` returning `Err`.
     2. With a gated first player, register the wake, call `set_volume(0.5)` (refused), then release the gate.
     3. Assert that the wake fires once.
     4. Add a second case where the first player is released and settled before `set_volume`, with the wake registered after it settled. This shows that a wake put back late still fires.
3. **docs/decisions/account-scoped-ui-state.md:10259, 10289, 10290, 10295, 10300. Doc, confirmed.**
   - What is wrong: the round 4 table supersedes earlier rows, but they still state the old behaviour:

     - 10259, round 2 recheck timer: "starts a check only from Idle, UpToDate, NoRelease or Failed". `DownloadFailed` is in that list now.
