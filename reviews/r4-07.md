# Review of r4-07 (Opus, 2026-11-12). Verdict: fix round

- src/ui/signin_ui.rs:847-858 `reset_login_email` (regression from the auth_ui.rs / auth_state.rs change). The old `auth_submit_busy` counted `ResetAuthenticationEmail` through the `has_auth_submit` purposes. The new `AuthSubmit` stage only knows requests passed to `submit.sent(..)`, and this call never passes one. Trigger: on the email-code step, press "Reset email" and then press Submit (or Enter) before the answer. Effect: no spinner, and Submit and Reset stay enabled, so `checkAuthenticationEmailCode` (or a second reset) goes out alongside the reset. Fix: `let result = live.driver.reset_login_email(); self.screen.auth_ui.submit.sent(&result);`, then build the note from `result`, and add a test that a reset holds the submit busy.
- src/ui/appearance_power.rs:128-136 (Linux system accent). When the stage is `Reading` and `started` is true (the previous read thread finished and a new one started, but the previous wait task has not run yet), the code only overwrites `known` and returns. The new read's `landing` receiver is dropped, so that read's result is never applied until the next refresh. The old `while pending()` loop picked it up. Fix: keep the old wait only when `!started`; when `started`, replace the stage's wait with a new task awaiting the new `landing`. Also, the doc at lines 110-113 still says "a short poll applies the result"; it should describe the receiver wait.
- src/ui/bottom_action.rs:178-196 (13-004). Adopting `pending_unblock` makes two consumers of one ack, because src/ui/web_app_ui/phone.rs:134-141 also `acks.expect`s and `take`s the same request, and acks are single-consumer. Trigger: the web app's phone flow unblocks the bot while the chat's bottom Unblock is shown. Whichever pump runs first takes the answer, and the other waits forever (a spinner that never ends, or a phone request never answered). `acks.forget(old)` on replace can also drop the answer the phone flow is waiting for. Fix: don't adopt a request another surface already awaits (adopt only one the bar sent), or key ack waiters by surface so each can take its own copy. Add a test with both waiting.
- src/ui/call_add_people.rs:93-97 together with src/state/conference_add_people.rs:157-160 (the twin of 14-007, which the bundle fixed only for the other list). The box shows "Loading contacts" whenever `data().is_none()`, and that includes the `Failed` fetch. Trigger: the contacts fetch fails (offline or a TDLib error) while Add People is open. Effect: "Loading contacts" stays forever, with no Retry. Fix: match the fetch, show the error with a Retry that re-sends the fetch on `Failed`, and add a test.
- scripts/stage-enums-allow.txt:25 still reads `unkeyed:SearchField::Opening src/ui/call_add_people.rs ...`, but the variant is now `SearchField::Unbuilt`. This allow line is stale and matches nothing. Fix: delete the line, or, if the guard still needs it, reword the key to the new name in the same commit with a note in the decision table.
- src/ui/auth_state.rs:73-98. `AuthSubmit::Out { request }` never leaves `Out` after the answer; "busy" is worked out by asking the registry whether the request is still there. RequestIds come from a per-session counter (src/state/requests.rs:424/459), so after `live` is replaced (sign-out, then add account) while `AuthUi` stays, a stale id can match an unrelated request in the new session. Trigger: submit, sign out, start a new login whose counter reaches the same id. Effect: the form shows busy for someone else's request. The final sweep would record this as a stage that has no way out. Fix: drop to `Idle` once the request is no longer in the registry (in `sync_auth_forms`), and reset to `Idle` when `live` is replaced.
- src/ui/bots_extras.rs:381-385. The Add Bot box decides "Loading" vs "Couldn't load" with a purpose query (`has_purpose_for_user(GetUserFullInfo, bot_id)`), not with the session's `users_state.user_full_infos` Fetch. A full-info request sent for another reason reads as loading, and a failed fetch whose purpose entry is gone reads as plain "Couldn't load", with no link to its Retry. Fix: read the Fetch's `shows_loading()` / `error()`, as chat_appearance_dialog.rs now does for boost status.
- src/ui/chat_bars.rs:434-447 `submit_bar_report`. It shows `REPORT_SPAM_DONE` as soon as `report_chat` and `leave_channel` are sent, not when they are answered. A refused report still reads "done". Fix: hold the two RequestIds and set the note from their acks (or show a silent "Reporting…" note and the result on the answer).
- src/ui/attach_bots.rs:75-84 (S4). A missing or non-SVG icon still calls `std::fs::metadata` on every render of the attach menu, and the first read happens on the UI thread. Fix: remember the unusable verdict per file id in the icon cache, the same way a read SVG is kept.
- src/audio/output.rs:150-152. The `Watch` doc says the thread "ends at its next look", but the change now wakes it at once. Fix: update the doc.
- src/ui/bot_create_dialog.rs:499-508 builds its own `Rc<Cell<Option<..>>>` body slot instead of the shared `crate::ui::shell::one_shot_dialog_content`, which this bundle adopted in cancel_edit_confirm.rs. Fix: use `one_shot_dialog_content(body)`.
