## Defects introduced by the bundle

- **src/ui/gifs_ui.rs:347-351 (16-008): request loop. S2, plausible.**
  - What changed: `gif_tab_upkeep` now asks again from `Asked(_)` as well as from `Wants(_)`. No other reader tells the two apart, so `Asked` has become `Wants` under another name. The "asks once" in the comment and in the `GifTab` doc is not enforced anywhere.
  - Trigger:
    1. Chat window B has its GIF tab on a search that the server keeps failing. Failed searches are not kept in `searches_kept`.
    2. Window A was pressed last and shows a kept search "q".
    3. B's upkeep sees `Missing`, nothing on its way and `Asked`, so it asks "x". The ask fails.
    4. A's `follow_gif_wanted` sees `Found(q)` with nothing on its way and asks "q". Now B sees `Missing` again, and the cycle repeats.
  - Effect: endless getInlineQueryResults/search traffic and redraws while both tabs are open. Before the bundle, `Asked` never asked again.
  - Fix: record how the ask ended, as `Asked { wanted, ended: AskEnd::{Answered, Failed} }`. Ask again only from `Answered` when `gif_shown` is `Missing`, and go to `Asked { ended: Failed }` from an error. Alternatively, keep failed searches in `GifSearches` so `gif_shown` returns a failed `Found`, not `Missing`.
  - Add a test: two windows, one failing search, and assert a bounded send count.

- **src/ui/folder_share/invite.rs:113-117 and :160-170 (16-004): add error lost. S3, confirmed.**
  - Trigger: press Add on folder link 1. While the add is out, open addlist link 2. The add then fails, or hits `LimitHit`.
  - What happens: `settle_folder_invite` puts the box in `Ready { error: Some(line) }` and returns `next`. `drive_folder_invite` then calls `open_folder_invite(link2)`, which replaces the whole box with link 2's check.
  - Effect: the add error is never shown (no toast, and the form holding it is gone), so the user cannot tell folder 1 was not added.
  - Fix: in the `Failed` arm, when `next.is_some()`, also call `set_note(StatusNote::error(line.clone()))`. Better: keep the failed form and check the queued link only when that box is closed or after Done.

- **src/ui/folder_share/invite.rs:55-77 (16-004): close reopens the box. S4, confirmed by reading.**
  - What happens: `close_folder_invite` reopens the box from inside the close when a link is queued.
  - Trigger: `run_close` / `close_blocked_dialogs` in shell.rs call the close again until the open flag clears (window closed, agent block).
  - Effect: the first call opens link 2 and sends `checkChatFolderInviteLink`. The second call closes that box and drops the check. The queued link is lost without a word, and a request is wasted.
  - Fix: do not reopen inside the close. `cx.defer` the reopen, or keep the queued link with the `ClosedAsk::FolderAdded` entry and open it from the poll when that ask settles. Fix the "box-host" comment to match.

- **src/ui/folder_share/invite.rs:25-28 (16-004): same link opened twice. S4, plausible.**
  - Trigger: the same addlist link is opened twice while Add is out (double click).
  - Effect: after the add succeeds, a second box pops up for the folder just added.
  - Fix: queue only when `link != dialog.link`.
  - Add tests that the queued link opens after Done, Failed, LimitHit and close. The current test (folders/box_stage_tests.rs) only checks that the link is queued.

- **src/ui/dialogs/data_storage.rs:34-46, 77-79, 99-102 (g-255): rename that dodges a guard, plus a regression. S4, confirmed.**
  - What changed: `StorageScrollStage::Requested` became `Requested { until }`. This adds a polled `Instant` deadline (2 s, checked from render), which is the shape 15-004 removed. The variant now has a field, so the bare-variant rule stops matching, and the allow line was deleted.
  - Why the deadline guards nothing: `Requested` is only set while Settings is on Data & Storage, and every way off the page goes through `leave_data_storage`, which resets it to `Idle`.
  - What it adds: a lost scroll. Press "Manage local storage" from the disk banner in a chat window while the main window is minimized. If the main window's first frame comes after 2 s, Settings opens at the top.
  - Fix: restore the base code (bare `Requested`) and the base allow line for `bare:StorageScrollStage::Requested`, whose reason is accurate. This is a restore of the base, not a new allow line. Drop `SCROLL_REQUEST_LIFE`.
