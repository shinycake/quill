# In-flight variants that wait for nothing Quill started (scripts/check-stage-enums.py).
# One per line: <rule>:<Enum>::<Variant> <reason>
unkeyed:Stage::Decoding src/sticker_playback/player/engine.rs: the clip holds the index of the opener thread decoding it, which is what ends it: `WorkerEnd` (dropped when that thread returns, panics or never starts) fails every clip of its index (`State::opener_ended`). The index is a `usize`, which the check cannot tell from plain data
bare:StartupStep::Waiting src/tray_reveal.rs: what one look at the tray returned ("look again soon"), not a stored stage. The stored stage is `StartupWatch::Watching { since }`, which holds its deadline
bare:GiveawayLaunch::Verifying waits on the person at the payment provider's verification page (3-D Secure), which sends Quill no answer; it was Verifying { chat_id } in the baseline and is now the value of that chat's entry in GiveawayLaunches. "Start over" on the form (end_verification) or the end of the session leaves it
bare:CloseFriendsStage::Awaiting src/story_extras.rs: the editor is open before the list arrived and keeps no copy of the load. The fetch (with its request, its failure and the Retry) is the session's `CloseFriendsList`, which the panel reads while the editor awaits; the upkeep moves it to `Editing` when that list is loaded, and Cancel or the viewer closing leaves it
bare:DownloadStage::Running src/spell_download.rs: one atomic byte shared with the download worker thread, so it cannot hold a handle. It only moves forward: the worker ends it (`Done`, or `Cancelled` after a stop request), and the UI's stop request only moves `Running` to `Cancelling` in the `Progress` both sides share
unkeyed:BotStopStage::Running src/state/bot_stop.rs: the bot is still writing its reply, TDLib's own `updatePendingMessage` state with its `can_stop`; no request of ours (the Stop that is ours is `Stopping(RequestId)`).
bare:Launch::Starting src/telegram/hub.rs: TDLib is still opening its database and no client claimed the launch page; TDLib's own start, nothing Quill asked for. The first frame does not wait in this stage.
unkeyed:Launch::Asked src/telegram/hub.rs: holds the client whose first page the first frame waits for; that client's page or the wait's cap ends it. The stage is shared with the receive thread under a mutex and a condvar, so it cannot hold a Task.
bare:RunStage::Running src/telegram/hub.rs: the receive thread's own lifecycle, shared with that thread under a mutex. The hub holds the thread's JoinHandle beside it (`Hub::thread`) and joins it on stop.
bare:RunStage::Stopping src/telegram/hub.rs: a stop was asked of the receive thread; the loop's next check ends it and the hub joins the JoinHandle it holds beside the stage.
bare:EntryStage::Loading src/ui/image_budget/entry_stage.rs: what `use_image` last returned for the entry. The decode is GPUI's image load, held beside the stage (`Entry::load`); dropping the entry drops it.
bare:CallRating::Sent src/state/call_types.rs: the answer to the rating's `Sending { request }` arrived, so nothing is in flight in this value; it is the end state that keeps the card from coming back
bare:CallUpload::Sent src/state/call_types.rs: the answer to the upload's `Sending(request)` arrived; this is the finished state, not work in flight, and nothing leaves it
unkeyed:CallTransport::Connecting src/state/call_types.rs: the engine's own report of the media transport (connect issued, or the engine says it is connecting); the engine's next state report ends it (`TransportState` Connected, Reconnecting, Failed or Closed), and a call that ends drops it. Quill holds no request for it; the `CallLink` is the retained connect parameters
unkeyed:Capture::Waiting src/ui/keybindings/capture.rs: the Shortcuts row waits for the user's next keystroke; nothing Quill started. A saved chord, Escape, Cancel, the row's reset or a refused chord (`stop_capture`, `reset_row`, `refuse_chord`) ends it, and leaving the page, locking or an account change ends it (`end`, `invalidate_account`)
bare:Phase::Opening src/ui/video_player/controls/live_overlay.rs: a pure function of the player's `PlayState` (`phase(LiveInput)`), computed per draw so the overlay clock can remember when a phase began; the player reports Opening, Quill holds no request for it
unkeyed:LiveOverlay::Opening src/ui/video_player/controls/live_overlay.rs: the overlay drawn for the player's Opening state, derived per draw from `phase(LiveInput)` and `overlay_at`; it holds the spinner flag of that moment and nothing in flight
bare:OutboxReceipt::Sent src/state/chat_types.rs: a mark derived at draw time from `last_read_outbox_message_id` (`ChatSummary::outbox_receipt`): the message reached the server and the peer has not read it. No request is involved and nothing is stored
bare:RowStatus::Sending src/state/chat_types.rs: a mark derived at draw time from the last message's `MessageSendState::Pending` (`ChatSummary::row_status`); the send itself is tracked by its own request elsewhere
bare:RowStatus::Sent src/state/chat_types.rs: a mark derived at draw time from the outbox receipt (`ChatSummary::row_status`); delivered, not yet read
bare:WithdrawalState::Pending src/premium_hub/ton.rs: TDLib's `RevenueWithdrawalState` of a Fragment withdrawal mirrored as is (the server's own state of the payout); Quill started nothing
bare:Delivery::Sending src/ui/message_text/mod.rs: a message's footer mark, computed at draw time from the message's own `pending` and receipt (`Delivery::of`); nothing is in flight in this value and nothing answers it. The send itself is the outbox's stage
bare:Delivery::Sent src/ui/message_text/mod.rs: as `Delivery::Sending`: the receipt the server gave, mirrored for the footer
bare:MenuFile::Downloading a fact about the row's file read while a menu is built (the download stage lives in the downloads table); nothing is held or waited for
