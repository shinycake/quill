## Drafts everywhere — cloud drafts keyed by (chat, topic) (2026-10-11)

- **Gap:** `Session::accepts_composer_draft` only said yes for private chats with a non-bot user. Groups, supergroups, channels the user posts in, bot chats, secret chats, forum topics and reply threads never saved or restored a draft, and the topic list never showed one. Telegram Desktop keeps a draft per `(history, topicRootId, monoforumPeerId)` (`Data::DraftKey`, data/data_drafts.h) and saves it wherever the compose field is shown (`ApiWrap::saveCurrentDraftToCloud` runs for the active thread, whatever the peer); a comments / replies view resolves its key to the thread root (`ChatWidget::resolvedTopicRootId` returns `_repliesRootId`, forum or not); the chat list shows "Draft:" for any row whose thread has a non-null cloud draft and nothing unread, except rows displayed as a forum (`dialogs_layout.cpp`, `cloudDraft` lambda), and topic rows show their topic's draft the same way (`ForumTopic::applyTopic` applies `vdraft`).

### Audit of the flow before this slice

- UI (`ui/drafts.rs`): every composer change calls `note_open_draft(delayed=true)`; chat switches (`select_chat_with`, search result, deep link, Saved Messages) call `flush_leaving_draft` / `leaving_draft_parts` before and `restore_open_draft(window)` after. Both read only `chat.draft`. Topic selection (`select_topic_ui`), thread open / close (`open_thread_view`, `advance_thread`, `leave_thread_view`, `view_thread_in_chat`) did neither, so the composer text leaked from the chat into its topics and threads and back.
- Driver (`connect/composer.rs`): `note_composer_draft` → `DraftSaveClock` (tdesktop `kSaveDraftTimeout` 1 s / `kSaveDraftAnywayTimeout` 5 s) → `PendingDraft {chat_id, text, reply}` → `commit_debounced_draft` → `setChatDraftMessage` with `topic_id: null`; `clear_draft_after_send` sends a null draft after `updateMessageSendSucceeded` (`messages.draft_clears`) when the composer is idle.
- Reducer: `chat.draft_message` (`updateNewChat`) and `updateChatDraftMessage` fill `ChatSummary::draft` unless `messages.draft_dirty` (a `HashSet<i64>` of chat ids) says the composer has unsaved text. `ChatSummary::draft_preview` → `SidebarLine::Draft` → red "Draft:" prefix in `ui/chat_row`, hidden behind unread and for forum chats. `forumTopic.draft_message`, `updateForumTopic.draft_message` and `messageThreadInfo.draft_message` were parsed away.
- Reply context: `ChatDraft {text, reply_to_message_id, quote}` round-trips `inputMessageReplyToMessage` + `inputTextQuote`; the restore looked the replied-to message up in the chat history only.

### Built

- `composer::DraftTopic { Chat, Forum(i32), Thread(i64) }` (+ `DraftKey`): the topic half of a draft key; `Chat` is TDLib's `topic_id: null`. Direct-messages topics (`messageTopicDirectMessages`) are not modelled because Quill has no `directMessagesChatTopic` support yet; Saved Messages topics get no slot because tdesktop only keys sublist drafts for monoforums (`_monoforumPeerId` is set only when `_sublist->parentChat()` exists).
- `state/session_drafts.rs`: `open_draft_topic(chat)` (open thread → `Thread`, or its forum topic when the thread was opened inside one — sends go there too; else open topic → `Forum`; else `Chat`), `accepts_composer_draft(chat, topic)`, `draft_for`, `store_composer_draft`, `mark_draft_dirty` / `draft_is_dirty` (keyed by `DraftKey`), `set_remote_draft` (dirty-aware), `keep_dirty_topic_drafts` (a refetched topic list keeps the draft a dirty composer started from), `draft_topic_of_message`, `draft_reply_preview` (chat, thread and topic histories), `ForumTopic::draft_preview`.
- Gate: `ChatSummary::can_post()` — users, bots, basic groups, supergroups, channels the user posts in (creator / admin with post rights), secret chats once `Ready`. TDLib refuses `setChatDraftMessage` where `can_send_message` fails, so a read-only channel is skipped before sending; for secret chats TDLib keeps the draft locally and still emits `updateChatDraftMessage` (`MessagesManager::set_dialog_draft_message`), tdesktop has no secret chats to compare with. A chat split into topics (forum, bot with topics) drafts per topic only: TDLib's `get_send_message_topic` for a bare forum chat is not something Quill sends to today, and tdesktop never shows a forum's chat-level draft. The dirty-check in `apply_update_new_chat` and `updateChatDraftMessage` moved to the `Chat` slot.
- Envelope: `ForumTopic::draft`, `ForumTopicUpdate::draft`, `ParsedMessageThreadInfo::draft` parsed with the existing `parse_chat_draft`. Reducer applies them in `apply_update_forum_topic`, the `forumTopics` / `getForumTopic` answers and `apply_message_thread_info` (stored on `ThreadView::draft`; TDLib has no update for thread drafts, `getMessageThread` returns `Message::thread_draft_message`, which is also where `updateDraftMessage` with `top_msg_id` lands).
- Request: `set_chat_draft_message(extra, chat, topic, text, reply)` with `draft_topic_value` → null / `messageTopicForum` / `messageTopicThread` (schema 1.8.68 lines 3311, 3314, 13887).
- Driver: `note_composer_draft_in(chat, topic, …)` with `note_composer_draft` deriving the slot from the session; `PendingDraft` carries its topic so a debounced save that fires after a topic switch still lands where it was typed; `clear_draft_after_send(chat, topic, idle)`; `draft_clears` is `Vec<(ChatId, DraftTopic)>` derived from the sent message's `topic_id`.
- UI: `flush_leaving_draft` reads the slot before the switch; `select_topic_ui` / `deselect_topic_ui` flush then request a restore (`composer_ui.draft_restore_pending`, run in `frame_upkeep` because menu-triggered switches have no `&mut Window`); `open_thread_view` flushes the origin slot before `getMessageThread`; `advance_thread` restores the thread draft once the thread starts in the same chat (the cross-chat case goes through `select_chat_with`, which already flushes and restores); `leave_thread_view` / `view_thread_in_chat` flush the thread slot before closing it and restore the chat's. The forum topic row shows "Draft: …" with the chat row's `draft_prefix` when `ForumTopic::draft_preview` says so. `consume_sent_reply`, `forget_local_draft` and the demo search paths use the open slot.

### Verified

- Reducer tests (`state/tests/drafts_everywhere.rs`): enablement per kind (user, bot, basic group, supergroup, channel member vs creator, secret ready vs pending, unknown chat; thread slots only in plain chats; forum: topic slots only), `forumTopic.draft_message` parse + topic row preview vs forum chat row, open-slot tracking across `select_topic` / `deselect_topic` / thread resolve / thread-in-topic, per-slot store + dirty with `updateForumTopic` and a refetched `forumTopics`, `messageThreadInfo.draft_message` restore and `draft_reply_preview` from the thread history, `draft_clears` slot per sent message, chat-level update still applied / ignored when dirty.
- Driver tests (`connect/tests/drafts_everywhere.rs`): group and bot saves with `topic_id: null`, read-only channel skipped; forum topic saves with `messageTopicForum`, explicit-slot flush after a switch, per-topic clear after send; a debounced topic save surviving a topic switch and ignoring a remote `updateForumTopic` draft meanwhile; comments thread (`messageTopicThread`) restore, save, clear, back to the chat slot.
- Request tests (`requests/tests_chats.rs`): `topic_id` shape per slot.
- Existing private-chat tests kept passing with the new signatures (`stories.rs` now asserts the bot chat drafts and the read-only channel does not).
- Gate (fmt, core + UI clippy `-D warnings`, core + UI tests), `check-hotspots.sh origin/main`, `check-file-size.sh`.

### Not done / reported

- Channel direct messages (`messageTopicDirectMessages`, tdesktop `monoforumPeerId`): Quill has no direct-messages topic model, so nothing to key on yet.
- Saved Messages sublists: tdesktop keeps one draft for the whole Saved Messages chat; kept as is.
- Forum "All" view: no chat-level draft, as in tdesktop.
- Rich / voice / video-note draft contents (`draftMessageContentRichMessage`, `…VoiceNote`, `…VideoNote`) are still not restored into the text field.
- No GPUI UI integration test: the repository has no `#[gpui::test]` harness yet; the switch paths are covered through the driver's `open_draft_topic` + `note_composer_draft_in` contract instead.
